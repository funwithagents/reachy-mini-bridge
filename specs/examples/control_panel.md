# Control panel (`examples/control_panel`)

**Status:** Updated

## Purpose

A Gradio web app for driving a robot by hand through [bridge.md](../core/bridge.md)'s `ReachyMiniBridge`: every verb has a button, and the bridge's readable state is on screen and kept fresh. It is a **manual test and demo tool**, not part of the shipped package — it lives in `examples/` and installs through the `demo` dependency group. Its config is set up on the page itself: the panel is built on the panels of `app-setup` (a `demo` group dependency) over the bridge's setup contract ([setup.md](../core/setup.md)), so the same page chooses the real robot, the simulator or the offline fake, a voice and its key, installs what is missing and prepares what a session would otherwise fetch or build itself (the models, the media registry), then runs a session on it.

Besides being the quickest way to exercise a verb without writing code, it is the worked example of calling the async api from sync code (a background event loop that sync callables submit to), and it makes the "Cancellation" contract of [bridge.md](../core/bridge.md) something a person can press: a Stop button next to `say`, `play_sound` and `play_emotion`.

## Core concepts / Decided

### Layout and how it runs

```
examples/control_panel/
  __init__.py      # package marker
  __main__.py      # `python -m examples.control_panel`
  controller.py    # ControlPanelController — gradio-free, owns the bridge session
  session.py       # RobotSession — gradio-free: the controller built from the saved config at Start
  app.py           # APP, build_page(model, session) -> gr.Blocks, open_panel(argv), main(argv)
examples/config_app/
  __init__.py      # open_model(argv), main(argv): one config file in the Setup and Secrets tabs, no session
  __main__.py      # `python -m examples.config_app`
```

- **Layers, the lower ones gradio-free.** `controller.py` imports the bridge, NumPy and the standard library only — no Gradio — so `tests/` exercise it on the `fake` backend without it; `session.py` adds app-setup's model and no Gradio either. `app.py` is the Gradio wiring: it maps components to controller calls and adds nothing the controller cannot do.
- **Run it as a module** from the repo root, so the example package imports the same way from the command line and from `tests/` (`pyproject.toml` adds `.` to pytest's `pythonpath`). It runs one of two ways — from its folder, or from a config file — and a third command edits a config file without a session:

  ```
  uv run python -m examples.control_panel [--folder DIR] [--env PATH] [--host ADDRESS] [--port N] [--start | --no-start]
  uv run python -m examples.control_panel --config FILE [--env PATH] [--host ADDRESS] [--port N] [--no-start]
  uv run python -m examples.config_app FILE [--env PATH] [--host ADDRESS] [--port N]
  ```

  `--folder` and `--config` are app-setup's `add_config_arguments` (one or the other), opened by its `open_source`; `--host` / `--port` (default `127.0.0.1:7860`) place the web server.
- **The app is bare: its config is the bridge's document.** `App(..., bare=True)`: the folder's `config.json`, a `--config` file, the config app's file and `App.default_config` all hold the bridge's config document itself (what `ReachyMiniConfig.from_dict` reads, any file of [examples/configs/](../../examples/configs/)), with no section around it; app-setup wraps it as `{"reachy": <document>}` for its panels and the model only. A folder written by an earlier version of the panel holds the wrapped shape, which the bridge refuses (`reachy` is not a field): delete it once, and the panel writes the default again.
- **From its folder** (the default): the **folder** (default `~/.config/reachy-mini-bridge-control-panel`, app-setup's `default_folder`) holds its saved config (`config.json`), its keys (`.env`) and its launch choice (`launch.json`); a new folder starts from the **default config**: the repo's full example config, [examples/configs/full.json](../../examples/configs/full.json) (every field), loaded into `App(default_config=...)` and written by app-setup into an empty folder at first launch, as the panel used it before ([config.md](../core/config.md), [sim_daemon.md](../daemon/sim_daemon.md)): the MuJoCo window opens next to the panel, the camera frame is the webcam, the voice is Phonon's, and with the motors enabled the simulated robot follows the person in front of it — the manual face-tracking check. On a fresh install the Setup tab shows what it needs (the `sim` extra, the voice's extra and model, the datasets); the offline fake is one field away (`backend: fake`).
- **From a config file** (`--config FILE`): the file is run as it is — read, never written: the Setup tab shows it read-only (Check, Install, Prepare and Test still work; there is no Save) — and its directory is the base of its relative paths (a `daemon.scene` file, a voice file) and where its `.env` is. The session starts at launch unless `--no-start`: running a given file is asking for it to run. A missing or unreadable file stops the launch with the reason (`parser.error`). The folder is not touched.
- **The keys**: the `.env` next to the config — the folder's, or the file's directory — unless `--env PATH` names another; the shell's variables win over it. The Secrets tab saves to that file.
- **A config app** (`examples/config_app/`, not a console script: the published package does not depend on app-setup): `python -m examples.config_app FILE` serves app-setup's `config_page` over the file — the panel's `APP`, `add_config_app_arguments`, `open_config_app` — the Setup and Secrets tabs with Save writing the bare document back to the file, and no session. The file must exist (copy one of [examples/configs/](../../examples/configs/)); a missing one is refused with the reason. `--port` defaults to gradio's (the first free from 7860), so it can run next to the panel.
- **The session starts at launch** (`App(autostart=True)`, app-setup's autostart): from its folder, unless the folder's launch choice says otherwise — the Setup tab's "Start the session when the app launches" checkbox — or `--start` / `--no-start` overrides it for one launch; from a file, unless `--no-start`. The panel starts its session from the saved config before the page opens (`open_panel(argv)`: the options parsed, the source opened, the model built, the session started — everything short of the web server, so tests drive it with the fake). A saved config with blockers (its problems, what the machine is missing) starts nothing: the blockers are logged and shown on the Robot tab, which starts once they are fixed. Ctrl+C in the terminal stops the server, then the session is stopped (which stops a daemon the bridge spawned).
- **Dependencies: the `demo` group.** `[dependency-groups] demo = ["gradio>=5", "app-setup[ui]", "reachy-mini-bridge[sim]"]` — Gradio, app-setup's panels, and the `sim` extra; the panel's voice comes from the config's `tts` block, whose provider the separate `tts` group installs (default in a plain sync, [project.md](../project.md) "Dependency groups"). It is a group of its own so it can be left out (`uv sync --no-group demo`), and it is in `[tool.uv] default-groups` next to `dev` so a normal dev env has it: `ruff` and `pyright` cover `examples/` (pyright's `include`), and that gate must not depend on which groups happen to be synced.

### The controller — one bridge session on a background loop

`ControlPanelController(config, *, synthesizer=None)` owns exactly one `ReachyMiniBridge` and exposes it to synchronous callers (Gradio handlers run in worker threads):

- **Lifecycle.** `start(timeout=None)` spawns a daemon thread running its own asyncio loop, which awaits `ReachyMiniBridge.start()` there — the pair, since the controller's `start()` / `stop()` are the host's own hooks ([bridge.md](../core/bridge.md) "Lifecycle") — caches `list_emotions()` (a failure is logged, the list stays empty), starts the mic meter task, and then waits. `start` returns once `bridge.start()` has returned, or re-raises what bring-up raised (the thread is gone by then); a timeout, or `stop()` during bring-up, cancels the bring-up task and the bridge unwinds what it started ([bridge.md](../core/bridge.md) "Bring-up is cancellable"). `stop()` cancels every in-flight verb, ends the loop's wait so the loop awaits `bridge.stop()` — in a `finally`, so it runs whether the wait ended or the session failed — and joins the thread. `with controller:` is `start()` / `stop()`. Every verb raises `BridgeError` when the controller is not running.
- **Instant verbs are plain blocking calls** that submit the coroutine to the loop and wait for its result: `get_motors_state()`, `set_motors_state(state)`, `start_head_tracking(focus)`, `stop_head_tracking()`, `set_head_tracking(enabled, focus)` (the two Gaze checkboxes: start with that focus, or stop), `set_posture(mirroring, approach, personal_space)` (the three posture checkboxes: `set_tracking` with each behaviour's `enabled`, the rest of `bridge.tracking` kept), `set_base_following(on)` (the Base following checkbox: `bridge.set_base_following` with `enabled`, the rest of `bridge.base_following` kept), `set_wobbling(on)`, `set_presence(on)`, `set_idle(mode)`, `set_face_detection(on)`, `camera_frame_rgb()` (the camera feed's newest frame, `bridge.camera.latest()` ([camera.md](../vision/camera.md)), flipped to RGB into a **copy** — the feed's image is shared and read-only — for display, `None` when there is none). Bridge errors (`MotorsNotEnabledError`, `GravityCompensationUnsupportedError`, …) and `ValueError`s propagate unchanged to the caller.
- **Spanning verbs block for their whole effect and can be stopped from another thread.** `say(text)`, `play_sound(path)` and `play_emotion(name)` return `True` when the verb completed and `False` when it was stopped; `stop_saying()` / `stop_sound()` / `stop_emotion()` cancel every in-flight task in that slot on the loop thread, wait until those verbs have actually returned (the bridge stops the effect *before* re-raising its `CancelledError`, so the wait is the guarantee that the speaker is silent, the sound file stopped or the trajectory no longer commanded), and return how many they stopped. A new `say` while one is playing interrupts the old one, and a new sound file the one playing — the bridge's own rules ([bridge.md](../core/bridge.md) "Cancellation": the newest `say` wins, the interrupted one raising `SpeechInterruptedError`; the newest sound file wins, an emotion's sound included, the replaced `play_sound` raising `SoundInterruptedError`), which the panel reports as that verb stopped (`False`); emotions are not pre-empted — the bridge queues them FIFO — so `stop_emotion()` stops the playing one and every queued one. `busy` reports the slots currently occupied (any of `"say"`, `"sound"`, `"emotion"`, or none).
- **`snapshot()`** reads everything the panel shows in one call and returns a `PanelState` dataclass: `backend`, `motors` (the daemon's motor state, or the error text when the read failed), `presence`, `idle` (the mode string), `wobbling`, `tracking` (`bridge.tracking.enabled`), `posture` (the followed face's `head_tracking` `roll_deg` / `offset_mm`, `None` while the head follows nobody), `base_following` (`bridge.base_following.enabled`), `body_yaw_deg` (where the base points, `bridge.body_yaw_deg`), `attention`, `face_detection`, `faces` (the number of faces in `bridge.faces.value`, `-1` when the report is inactive — no detector is looking), `face_positions` (each face's normalised `(x, y)`, in the report's order — by `track_id` ([user_perception.md](../vision/user_perception.md)); empty while inactive), `face_target` (the index in `face_positions` of the face the head follows — `bridge.head_tracking.value.track_id` looked up in the report ([head_tracking.md](../motion/head_tracking.md)); `None` while it follows none), `face_rate` (new face observations per second, `None` while inactive — see the face meter below), `voice` (`"ready"`, `"none"` when the config has no `tts` block and no synthesizer was passed, or `"unavailable: <cause>"` from `synthesizer_error`), `mic_level`, `mic_sample_rate`, `busy`, `emotions`. The six modes, `body_yaw_deg`, `attention`, `faces` and `synthesizer_error` are the bridge's own properties (plain reads); `motors` is a `get_motors_state()` round trip.
- **The face meter.** A task on the loop samples `bridge.faces.value` at `FACE_METER_HZ = 50` and records each report whose `ts` is new; `face_rate` is how many arrived over the last `FACE_RATE_WINDOW_S = 2` s, per second — the rate at which the detector's observations reach the bridge — the camera feed's rate, about 10/s under upstream's local-feed cap, since the detector runs once per new frame (the detection loop polls at 30 Hz, so it misses none). It counts observations, not faces: an empty room still reports at the detector's rate. On the fake it counts the frames a registered stub detector has seen.
- **`draw_faces(frame, positions, rolls=(), target=None, *, labels=(), mirror=False)`** returns a copy of an RGB frame with a green square outline centred on each face (normalised coordinates → pixels, side 15 % of the frame height, the face at index `target` drawn thicker, none when `None`), tilted by the face's roll when it is known (`Face.roll`; drawn before the display mirror, so the tilt mirrors with the picture), the copy flipped left to right when `mirror`, and each face's label (`labels[i]`, the panel's `#<track_id>`) stamped above its square — below it when there is no room above — in green on a black plate, **after** the flip, so the text reads the right way round on the mirrored view — plain numpy and a built-in 3×5 bitmap font of digits and `#`, scaled with the frame's height, no vision code. The camera tick takes positions, rolls, track ids and target from the controller's **`face_view()`**, which reads them off **one** face report, so a report published between two reads cannot pair one frame's markers with another's target, tilt or id.
- **`users_view()`** reads the users present and whom the head follows in one call (no robot round trip) and returns a `UsersView`: `active` (a detector is looking, `bridge.users.value.active`), `users` (the `User`s of `bridge.users.value`, in `track_id` order — [user_perception.md](../vision/user_perception.md) "The users present": kept through a move of the robot's own that takes them out of view, with `seen`, `in_view`, `missing_s`, their last sighting's `face`, `identity`), and from `bridge.head_tracking.value` ([head_tracking.md](../motion/head_tracking.md) "The head tracking report") `tracking` (`active`), `attention`, `track_id` (the user the head follows) and `pinned_track_id`.
- **The tracking events.** A task on the loop subscribes to `bridge.users.changes(every=True)` and `bridge.head_tracking.changes(every=True)` — every published report in order, so an arrival or a departure is never skipped between two polls — and keeps the last `TRACKING_EVENTS = 50` events as timestamped lines (`HH:MM:SS.mmm`, the time the panel received them), read newest first by **`tracking_events()`**: from the users (`describe_users_change(previous, report)`, a pure function), `#4 arrived`, `#3 left (left)` / `(unseen)` / `(stopped)` with the departure's reason, `#4 recognised as <key>`, `detection on` / `detection off` on an `active` flip; from the head tracker (`describe_tracking_change(previous, report)`, a pure function), `tracking on` / `off`, `focus on` / `off`, `head follows #4`, `head #3 → #4` on a switch, `head lets go of #3 (watching)`, `pinned #3` / `unpinned`, `#4 entered` / `left personal space`. It is the record of how the ids went: a person whose track breaks during an emotion shows as their departure and a new id's arrival, a person kept through it as nothing at all.
- **The mic meter.** A task on the loop iterates `bridge.audio_input()` (mono int16) and keeps `mic_level` — the RMS of the latest chunk on a 0–1 scale, held with a short exponential decay so a 0.5 s refresh still shows a burst — paced at half the chunk's duration so it never spins on a backend that always has a chunk ready (the fake). A failing tap is logged and leaves the level at 0; it never brings the panel down. On the fake the level reads 0 (synthetic silence).

### The session — `RobotSession`

`RobotSession` (`session.py`) is the one session the page runs, built when Start asks for it:

- **`start(model, timeout=None) -> list[str]`** reads the saved config (`model.saved_config()`); with blockers (`model.blockers(saved)`: the config's problems and its **required** items missing — an item a session gets by itself, the face detector's weights, the emotions library, GStreamer's registry, does not block, the first start fetches or builds it, slower) it returns them and builds nothing; else it builds a `ControlPanelController` from the `reachy` section (`model.used_config(saved)["reachy"]`, through `ReachyMiniConfig.from_dict(section, base_dir=model.path)`: the app's folder — or the config file's directory — is the base of the config's relative paths — a `daemon.scene` file, a voice file — the same folder app-setup passes to the setup functions as `base_dir`, so Check, Prepare, Test and Start look at the same file) and starts it — returning `[]`, or the one reason it could not (a bring-up that raised, a timeout). Already running, it returns `[]` and keeps the session.
- **`stop() -> bool`** stops the controller (its verbs, the session, a daemon it spawned) and forgets it; `False` when nothing ran.
- **`status`** is `starting` from a Start until the session runs or did not start, `running`, `stopping` from a Stop until it is stopped, else `stopped` — what the Start and Stop buttons follow.
- **`locked()`** is true from Start until the stop finished — what the model's `locked` is given, so the Setup panel refuses Save and Reset while a session runs on the saved config; stop the session to change it.
- **`require()`** is the running controller, else a `BridgeError` ("no session is running: press Start"), which every Robot-tab handler turns into a toast.

The keys reach the voice through the environment: app-setup loads the config's `.env` (next to it, or `--env`) under the shell's variables when the model is built.

### The UI

`APP` declares the app to app-setup: `App(name="reachy-mini-bridge-control-panel", title="Reachy Mini control panel", host="reachy-mini-bridge", sections=(Section("reachy", reachy_mini_bridge.setup, title="Reachy Mini"),), default_config=DEFAULT_CONFIG, autostart=True, bare=True)`, `DEFAULT_CONFIG` the document of `examples/configs/full.json` — the host is the bridge itself, so "Install missing extras" installs its own extras (`sim`, `placo`, `tts-<extra>`) from its lock. `build_page(model, session)` returns a `gr.Blocks` of three tabs: **Robot** first, then app-setup's **Setup** panel (`setup_panel(model)`) and its **Secrets** panel (`secrets_panel(model, setup.draft)`, following the Setup panel's draft). It opens on **Robot** when the session starts at launch (`starts_at_launch` true: `build_page(..., started_at_launch=True)`), its blockers shown there if it could not, else on **Setup**.

The Robot tab reads top to bottom: **Start** and **Stop** with a session line (`starting…`, the backend running, `stopping…`, `no session`, or why it cannot start: the blockers as a list), under it app-setup's `unsaved_notice` — "The Setup tab has unsaved changes: Start uses the saved config." while the Setup tab's draft differs from the saved config, refreshed on the draft's and the saved config's changes — **Start enabled only while the session is stopped, Stop only while it runs** (`session_buttons`): a press greys both at once, its outcome sets them, and the 0.5 s timer refreshes them with the line, so a session started at launch or from another browser tab shows right — the effective config read-only in a collapsed accordion, the controls, then what the robot sees and hears beside what it detects and whom it follows, then its state beside the logs. Its controls take their initial values from the saved config when the page is built and again from the session's config at each Start (the modes, the posture, the motor state read, the emotions list); with no session, every verb shows a toast and the timers show the empty views (`no session`, a blank camera).

- **Controls** (top), one line each, grouped by [bridge.md](../core/bridge.md) verb group. First a row of three columns: Expression (dropdown from the cached emotions + Play + Stop), Speech (text + Say + Stop), Sound (a sound-file path + Play sound + Stop sound). Below them one **Modes** row, every control applied on user input: a Tracking and a Focus checkbox, both through `set_head_tracking(tracking, focus)` — a mode needing no motors, [bridge.md](../core/bridge.md) "Attention / gaze"; Tracking's and Focus's initial values are the config's `motion.tracking.enabled` / `focus` — Wobbling / Presence / Detection checkboxes, and an Idle dropdown over `breathing` / `hold` / `custom`; their initial values come from the config's `motion` and `face_detection` blocks. The panel registers no idle move of its own — it is started from a JSON file, which carries none — so `custom` shows the hold there. Under it a second row of three posture checkboxes — Mirroring, Approach, Personal space — through `set_posture`, their initial values the config's `motion.tracking` sub-objects' `enabled`, and a Base following checkbox through `set_base_following`, its initial value the config's `motion.base_following.enabled`. Every checkbox carries a short label; what Focus, the posture and the body yaw mean is one italic line under the rows. Last, **Motors** on one line: the radio `enabled` / `disabled` / `gravity_compensation` with Apply on its right.
- **Camera and mic** (below the controls, left): the camera frame as an image with a marker on each reported face and its `#<track_id>` label (`draw_faces`), shown **mirrored** like a selfie view (`MIRROR_CAMERA`, display only: `camera_frame_rgb()` and the faces table keep the bridge's image coordinates, x right as the robot sees it; the labels stay readable), refreshed by its own `gr.Timer` at 0.2 s (the image is blank when the backend has none — the headless sim on macOS); under it the mic level as a read-only slider.
- **Detection and tracking** (beside the camera, right), refreshed on the camera's 0.2 s timer, in three subsections whose headings carry their live summary:
  - **Faces** — who is in the frame, from `face_view()` and the face meter (no motor round trip): a **faces table** in the users table's format, one row per face in the report's order: `#id` (`●` on the one the head follows), normalised position, size, roll in degrees and distance in metres (`—` when the report does not give them) (`— (no detector is looking)` while inactive, `nobody in view` when empty); the face update rate in the heading, `Faces (10.0 updates/s)`, the bare `Faces` while no detector is looking — so ids and numbers follow a moving face and a face that changes id shows it at once.
  - **Users** — who is present, from `users_view()`: a **users table**, one row per user: `#id` (`●` on the one the head follows, `📌` on the pinned one), `seen`, `in view`, `missing` (s), the last sighting's position, size and distance, and the identity key when one is held (`— (no detector is looking)` while inactive, `nobody present` when empty). Through an emotion that turns the head away, a person stays in the table, `in view` no, under the same id.
  - **Head tracking** — whom the head follows, in the subsection's heading itself, from the same `users_view()`: `Head tracking: following #4` (`· pinned` when it is the pinned one), `following nobody (watching)` (`, pinned #3 lost` while a pinned user is lost), or `Head tracking: off`, with `· focus`. The followed user's state is their row in the users table.
- **State and logs** (a row of their own, under the camera and the detection), refreshed with the mic level by a `gr.Timer` at 0.5 s from one `snapshot()`: on the left one table in two halves side by side — the session (backend, motor state, attention, the posture — `roll +5°, lean +12 mm`, with `in personal space` while the followed person is in it — the body yaw, `+35°`, where the base points, voice, what is busy, the mic's sample rate) left, the six modes right; on the right the logs in two tabs — **Log**, the last 50 outcomes (each verb's completion, stop, or error, timestamped), and **Tracking events**, `tracking_events()` newest first, refreshed with the users on the camera's timer.
- **Every handler is a named endpoint** (`api_name` = the verb, plus `refresh`), so the panel doubles as a small HTTP API: `gradio_client.Client(url).predict("happy", api_name="/play_emotion")` drives the same controller from a script.
- **Errors never crash a handler.** A `BridgeError`, `ValueError` or `FileNotFoundError` (a sound file that is not there) from a verb becomes a `gr.Error` toast with the exception's message and a log line; a stopped `say` / `play_sound` / `play_emotion` logs "stopped", a completed one "done".

### What the panel shows honestly

The panel displays what the bridge reports, so backend limits show as they are: the MuJoCo sim ignores motor-state changes and keeps reporting `enabled`; the headless sim (`daemon.headless: true`) returns no camera frame on macOS, while the viewer the example config opens does; `say` on a config without a working `tts` block reports the voice as `none` / `unavailable` and the Say button surfaces the bridge's `BridgeError`.

### Tests

`tests/test_control_panel.py` drives `ControlPanelController` on the `fake` backend the way the app does — from a caller thread — and asserts through `bridge.robot` (the `FakeReachyMini`'s recorded commands): bring-up and teardown, instant verbs dispatching and their errors propagating, `snapshot()` reflecting mode changes — the base-following switch and the body-yaw readout among them — and the face count, positions and update rate as a stub detector registered through `face_detection.detector: "custom"` shows a face on the fake's frames ([user_perception.md](../vision/user_perception.md) "`fake` backend support"), `draw_faces` marking the face's pixels and stamping each label upright on a mirrored frame, the users view and the tracking events following a stub face's arrival, the head engaging it and its departure at a stop, `describe_users_change` / `describe_tracking_change` naming each transition, the users table marking the followed user and who is out of view, and, per [AGENTS.md](../../AGENTS.md) "Testing", the three spanning verbs stopped mid-flight from another thread (the speaker flushed / the sound stopped, the verb returning `False`, the session still usable). `RobotSession` over a model in a temporary folder: a missing item a session gets itself does not block Start, a required one does; Start builds the session from the saved section — a relative voice file found in the app's folder, not the working directory — `locked()` holds from Start to the end of Stop and the model refuses a save meanwhile, a config with blockers starts nothing and says why, a bring-up that fails is a reason and leaves nothing running, Stop with nothing running is `False`; the default config is the committed file, written into an empty folder as the bare document, and has no blockers; a saved config lands in `config.json` as the bridge's document; from a config file (`open_panel(["--config", FILE])`, a fake config): the session runs on it at launch, the model is read-only and refuses a save, its base is the file's directory and the file and the folder are left untouched, `--no-start` starts nothing, a missing file stops the launch with its name; every file of `examples/configs/` has no problems as the panel's config; the config app saves a bare document back to its file, keys to its `--env`, and refuses a missing file; the page puts Robot first and opens on Setup, on Robot when the session started at launch; Start and Stop follow the status (stopped: Start only; starting, mid-Start: neither, the line `starting…`; running: Stop only; a Start that started nothing: Start again); a smoke test builds the page over a started session and reads one tick of each timer, and the ticks with no session show the empty views.

## Open questions

None load-bearing. Deferred extensions, each a small addition: a "record N seconds and play it back" mic widget next to the level meter; a few raw `bridge.robot` readouts (head pose, IMU) once [bridge.md](../core/bridge.md)'s rich-perception verbs land.
