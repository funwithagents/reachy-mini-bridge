# The bridge (`ReachyMiniBridge`)

**Status:** Implemented

## Purpose

`ReachyMiniBridge` is the object a caller holds to drive the robot: the high-level, intention-level surface — **human intent and human units**: "look at this point", "nod", "play the happy emotion", "say this", in degrees / seconds / named emotions, where the upstream SDK speaks in 4x4 pose matrices and radians — and the running system behind it. It orchestrates the lower-level [robot.md](robot.md) primitives (the motion loop's target stream — [motion.md](../motion/motion.md) — recorded moves, and media) into single semantic verbs, and while it runs it keeps the robot alive on its own, with nobody calling a verb: the motion loop breathes and follows a face, the camera feed reads, the detection loop watches. The name says what it is — the bridge between the robot and whatever drives it, the same word as the package — and its lifecycle is a session's, `start()` / `stop()` ("Lifecycle" below).

It is the layer a human, service, or agent runtime codes against directly. **Action verbs** take and return plain, JSON-friendly Python values, so a caller can wrap them as agent/LLM tools as they stand. **Perception verbs return the natural rich object** instead — a camera frame is a `CameraFrame` holding the numpy BGR array ([camera.md](../vision/camera.md)), the mic is a raw-PCM stream ([audio.md](../audio/audio.md)) — because that's what a Python caller wants to work with; encoding one for a model (e.g. a frame as base64 JPEG) is the caller's job, done at its own boundary.

### Driving the robot from an agent

An agent runtime uses the bridge the way any caller does, through tools its own code defines: each tool is a typed, docstring'd function that calls one verb (or reads one perception value) on a `ReachyMiniBridge` the agent holds open for its session. What makes the bridge fit for that:

- **Action verbs forward as they stand.** Their parameters and returns are JSON-friendly and in human units, so a tool's schema is the verb's signature: `play_emotion(name)` with `list_emotions()` as its menu, `say(text)`, `set_motors_state(state)`, `start_head_tracking()` / `stop_head_tracking()`.
- **Perception is read, then encoded by the tool.** `bridge.camera.latest()` hands over the newest frame and `bridge.faces.value` the current face report; the tool turns them into what its model takes (a JPEG, a count, a sentence).
- **Errors are named.** A refused verb raises a `BridgeError` subclass (e.g. `MotorsNotEnabledError`) whose message a tool can return to the agent as the reason.
- **A tool call is cancellable.** Cancelling the task running a tool stops the robot's action and leaves the session ready for the next call (see "Cancellation" below), so an agent's interruption is the bridge's interruption.

### Async-native

`ReachyMiniBridge` is **async-native**. Audio forces it (see [audio.md](../audio/audio.md)): speech synthesis is `async`, and a **live microphone stream** runs concurrently with playback and with the robot moving — full-duplex interaction (a caller's ASR consuming the mic while `say` speaks, plus barge-in) keeps both audio paths on one event loop.

- The upstream SDK's **blocking** calls (`enable_motors`, `get_status`, …) run under `asyncio.to_thread(...)`, and the 60 Hz target stream runs on its own thread ([motion.md](../motion/motion.md)), so motion never stalls the audio loops.
- The upstream `ReachyMini` is **synchronous** and mirrors the SDK 1:1; this layer is where async lives.
- A caller that needs **sync** callables runs its own background event loop and submits to it — the bridge stays async; the control panel ([control_panel.md](../examples/control_panel.md)) is the worked example.

### Cancellation — every async verb is fully cancellable

Cancelling the task that awaits a verb — `task.cancel()`, an `asyncio.timeout`, a `TaskGroup` unwinding — is the bridge's one interruption mechanism, so every `async` verb honors it fully. **"Fully cancellable" means three things, all required:**

1. **The cancel returns promptly.** The `CancelledError` reaches the caller at the verb's next `await`; a verb never swallows it and never holds the cancel until what it was doing would have ended on its own. The bound is one loop tick or one short SDK call: a blocking SDK call already running under `asyncio.to_thread` cannot be interrupted, so it finishes in its thread (a fraction of a second for every call the bridge makes this way) while the cancel propagates at once.
2. **The effect stops with the verb.** Whatever the verb was producing over time stops *before* the `CancelledError` propagates: queued speaker audio is flushed, a playing sound file is stopped, a trajectory is no longer commanded, the head wobbler is reset. The verb stops exactly what it started.
3. **The robot and the session stay usable.** A cancel undoes only the verb's own in-flight effect. Modes the verb did not set — `wobbling`, head tracking, the motor state — are left exactly as they were, the media session stays open, and the next verb works immediately: a cancelled `say` or `play_emotion` can be followed by another in the same breath. A `play_emotion` cancelled while it waits in the queue has no effect to undo: its sound never started, and the emotion playing ahead of it plays on — the motion loop stops only the sound it started, for the primary being cancelled.

What it does **not** mean: **no rewind.** An effect already delivered stays delivered — sound already heard was heard, and a cancelled move does not return the head to its starting pose. What the head does next is the presence behaviour's business, not the verb's ([motion.md](../motion/motion.md)): with presence on, the idle move blends in from wherever the cancel caught the head, exactly as after a completed emotion; with presence off the head stays there. Nor does a verb stop *another* verb's effect — with one exception, a `say` interrupting the `say` in flight (next paragraph); the deferred `stop_talking()` (below) is the planned other, for a caller who does not hold the `say` task.

**`say` is exclusive, and the newest call wins.** A `say` arriving while one is in flight interrupts it: the bridge flushes the running utterance's queued audio (the wobbler reset with it), logs one `INFO` line, and the interrupted call raises `SpeechInterruptedError` in its own task at its next `await` — the bridge never cancels a caller's task — while the new utterance plays from a silent speaker. This is `say`'s defined effect on a running `say` (an agent with something new to say does not queue behind the old sentence), not a breach of the isolation above, and the one way a verb ends another verb's effect ([audio.md](../audio/audio.md) "TTS out").

Verbs fall in two classes. **Spanning verbs** run for as long as their effect — `say`, `play_emotion`, the `audio_input` stream, and the session bring-up `start()` — and are where the three guarantees do real work; each has a test on the `fake` that cancels it mid-flight and asserts the effect stopped and the session still works, which is why the fake keeps real timing for them ([robot.md](robot.md)). **Instant verbs** — `set_motors_state`, `get_motors_state`, `start_head_tracking` / `stop_head_tracking`, `set_wobbling`, `set_presence` / `set_idle` / `set_idle_move`, `list_emotions` — hand one short command to the SDK (or the motion loop) and return; a cancel returns promptly and the command completes in its thread. Their effect, when it outlives the call, is a *mode* switched off by its counterpart verb, not something a cancel unwinds. `play_sound` is today an instant verb whose effect (a sound file playing to its end) has no counterpart — open question 3.

## Core concepts / Decided

- **Constructed from a config.** `ReachyMiniBridge(config: ReachyMiniConfig | str = "real", *, synthesizer: SpeechSynthesizer | None = None)` takes a [config.md](config.md) `ReachyMiniConfig` — backend, upstream connection options, daemon management, default synthesizer, audio profile — and builds the robot internally (see [robot.md](robot.md)): the real `reachy_mini.ReachyMini` for `real`/`sim`, our `FakeReachyMini` for `fake`, so the bridge is fully unit-testable on the `fake` backend. A bare backend string is shorthand for `ReachyMiniConfig(backend=...)`, so `ReachyMiniBridge("fake")` is the one-liner. The `from_dict(data, **kw)` / `from_json(text, **kw)` / `from_json_file(path, **kw)` classmethods mirror the config's constructor trio and build the bridge in one call — a host application's config file, JSON string, or dict yields a talking robot directly. The explicit `synthesizer=` keyword wins over the config's `tts` block, which is then not consumed; with neither, `say` raises `BridgeError` (see [audio.md](../audio/audio.md)). A `tts` block whose adapter build fails degrades to no voice rather than failing construction: every exception from building the adapter — tts-engine's `ConfigError` for a provider whose extra is not installed or a bad block, an unset key, a model that fails to load — is caught and recorded on the read-only `synthesizer_error: Exception | None` property (`None` when the voice built, when an explicit `synthesizer=` was passed, or when there is no `tts` block) and logged at `WARNING`. The bridge still comes up with no voice; `say` then raises `BridgeError` chained (`from`) to the recorded cause, its message naming it. The policy stays the host's: a host that wants hard failure checks `synthesizer_error` after construction and raises. A test asserts on the fake by reaching it back through `bridge.robot` (the escape hatch), not by injecting one.
- **Front door.** `from reachy_mini_bridge import ReachyMiniBridge` is the entry point: the package root re-exports exactly what a caller needs to drive the robot — `ReachyMiniBridge`, `ReachyMiniConfig`, the `SpeechSynthesizer` contract and its shipped `TTSEngineSynthesizer` adapter, the `IdleMove` / `IdleOffsets` contract of a custom idle move ([motion.md](../motion/motion.md)), the `Face` / `FaceReport` value of `faces`, the `HeadTrackingReport` value of `head_tracking`, the `PixelFace` / `FaceDetector` contract of a custom detector and the `Observable` type ([user_perception.md](../vision/user_perception.md)), the `CameraFrame` of the camera feed ([camera.md](../vision/camera.md)), and the `BridgeError` / `MotorsNotEnabledError` / `GravityCompensationUnsupportedError` / `ConfigError` errors a caller catches. Everything else (`MediaSession`, the conversion helpers, `FakeReachyMini`, `build_robot`, `AnyReachyMini`, `DaemonError`) is imported from its own module. The imports are eager: `reachy_mini` is a base dependency, and `TTSEngineSynthesizer` imports `tts_engine` only in its constructor, so the front door pulls in no extra.
- **Lifecycle: `start()` / `stop()`, and `async with` over them.** Construction stores the config and nothing else runs — no daemon, no connection, no thread. The lifecycle is the async pair `await bridge.start()` / `await bridge.stop()`, and the read-only `running` property (`bool`) says which side of it the bridge is on. `async with ReachyMiniBridge(...) as bridge:` is sugar over the pair — `__aenter__` awaits `start()` and returns the bridge, `__aexit__` awaits `stop()` — and is the recommended form wherever a caller can scope the session in one block, because the block runs `stop()` on every way out: a normal exit, an exception, a cancellation of the task. The pair itself is for hosts with lifecycle hooks of their own — a web framework's lifespan, a GUI's on-start / on-close, a module-scoped pytest fixture, an agent runtime opening the robot at boot — which call `start()` from one hook and `stop()` from the other. The same shape holds inside the bridge: every session it owns — the media session ([audio.md](../audio/audio.md)), the camera feed ([camera.md](../vision/camera.md)), the detection loop ([user_perception.md](../vision/user_perception.md)), the motion session ([motion.md](../motion/motion.md)) — exposes an `async start()` / `async stop()` pair as its whole lifecycle, and the daemon handle its synchronous `stop()` ([daemon.md](../daemon/daemon.md)); the block sugar exists on the bridge alone, the caller-facing object. Those inner lifecycles are the bridge's to drive, and a caller never reaches them: a caller switches *behaviour* through the modes (`set_presence`, `set_face_detection`, `start_head_tracking` / `stop_head_tracking`, `set_wobbling`), which change what the running workers do while the workers keep running — the one-writer, always-alive principle ([motion.md](../motion/motion.md)) rests on the bridge being the sole owner of its threads.

  `start()` brings everything up in order: the managed daemon when `daemon.spawn` is not `"never"` (the MuJoCo daemon for `sim`, a USB-attached robot's hardware daemon for `real`; `start_daemon` run off the event loop via `asyncio.to_thread`, see [daemon.md](../daemon/daemon.md)), then the robot (built with `build_robot(backend, **robot)` and entered — upstream's `ReachyMini` connects in its constructor, so it is built only once the daemon is ready), then the media session, then the **camera feed** ([camera.md](../vision/camera.md)) — the one reader thread over the robot's camera, stamping each frame with the head pose at its time through the motion session's `head_pose_at`, which is why the `MotionSession` object is constructed right after the robot (construction starts no thread) — then head wobbling unless the config's `motion.wobbling` flag turns it off (`set_wobbling(True)`, see "Audio-reactive motion" below), then the **detection loop and the head tracker** ([user_perception.md](../vision/user_perception.md) "Lifecycle") when a detector is configured and `face_detection.enabled` or `motion.tracking` is on — the loop builds the detector (a shipped one, or the registered custom one) off the event loop and samples the camera feed; a detector that cannot be built fails bring-up; the `MotionSession` object, constructed earlier, is what the tracker is wired to (`set_gaze` and `head_pose_history`), and only its thread waits — then, on the `sim` backend with `daemon.sim_displays.face_markers` on, the **face marker publisher** ([sim_displays.md](../daemon/sim_displays.md)) — a task that polls `bridge.faces` and sends each new report's faces to the daemon's viewer — then the motion session ([motion.md](../motion/motion.md)) — the loop thread that owns `set_target`, started with the config's `motion.presence` / `motion.idle` / `motion.idle_move` and paused unless the motors read `enabled`; when they do, the loop resumes, and the tracker's aim, if any, takes effect. Each step is one `start()` followed by its `stop()` pushed on an `AsyncExitStack`, so a failure at any step unwinds what already started and `start()` raises; `start()` on a running bridge raises `BridgeError`. `stop()` tears down in reverse: the motion session first (easing the head to neutral when presence is on and the loop is commanding), then the face marker publisher, then the detection loop, then wobbling whenever it is on, then the camera feed (its `latest()` reads `None` from then on), then the media session, then the robot, then an owned daemon, each even when another fails. The bridge reads as not running from the moment `stop()` begins; `stop()` on a bridge that is not running is a no-op; and it resets the modes to the config's values, so `start()` may follow it — a fresh session on the same object, on which `faces` and `camera` persist ([user_perception.md](../vision/user_perception.md), [camera.md](../vision/camera.md)). `bridge.robot` / `bridge.raw` are available only while running and raise `BridgeError` otherwise, since there is no robot object before the connection is made. **Bring-up is cancellable** (see "Cancellation" above): a cancel during `start()` — an `asyncio.timeout` around the `async with`, say — is handled like a failure. The step in flight (a daemon spawn, the robot connect, a media `start_*`) cannot be interrupted in its thread, so it is allowed to finish, then everything started so far is torn down, then the `CancelledError` propagates — nothing is leaked, at the cost of the cancel taking as long as that step (up to `daemon.startup_timeout` for a spawn).
- **Raw access preserved.** The underlying robot object stays reachable through the bridge as `bridge.robot` (a.k.a. `bridge.raw`) so nothing is a dead end — for `real`/`sim` it *is* the full native `ReachyMini`.
- **Human units.** Angles in **degrees**, durations in **seconds**, positions in a documented frame. The bridge converts to the upstream's matrices/radians internally (via `reachy_mini.utils.create_head_pose` and friends).
- **Idempotent, forgiving verbs.** Methods validate/clamp to safe ranges and fail with clear `ValueError`s rather than sending bad poses downstream.
- **Errors.** Out-of-range or unknown input raises `ValueError`. Errors from the bridge's own logic derive from `BridgeError(RuntimeError)` in `errors.py`: `MotorsNotEnabledError` is the *state* error a movement verb raises when torque is not `enabled` (see Motors), `GravityCompensationUnsupportedError` its sibling for a daemon that cannot hold that mode, `SpeechInterruptedError` what a `say` raises when a later `say` interrupted it (see Cancellation), and `DaemonError` covers the managed daemon ([daemon.md](../daemon/daemon.md)). `ConfigError` subclasses `ValueError`, since a malformed config is bad input ([config.md](config.md)). Connection errors are upstream `reachy_mini`'s, surfaced unwrapped.

### v1 scope — the minimum for interaction

v1 is deliberately narrow: the smallest verb set that makes the robot a **conversational, face-following** presence — **talk, listen, express, follow the person it's talking to, and stay visibly alive in between** (breathing, [motion.md](../motion/motion.md)). Manual movement/gaze and rich perception are explicitly **deferred to post-v1** (see below).

**In scope for v1:**

- **Audio out** — see [audio.md](../audio/audio.md)
  - `say(text, ...)` — synthesize speech via a **pluggable** `SpeechSynthesizer` ([audio.md](../audio/audio.md)); the default adapter wraps our first-party [`tts-engine`](https://github.com/funwithagents/tts-engine) (a base dependency; the provider comes from a `tts-pocket` / `tts-elevenlabs` / `tts-gradium` extra), but callers can supply any synthesizer. On a real/sim robot the audio is routed through the robot speaker (required for echo cancellation), not the local device. `say` **completes when the utterance has finished playing** on the speaker (not when it has merely been queued), and **cancelling the `say` task stops the speech** — the queued audio is flushed and the head wobbler reset — so `await bridge.say(...)` spans exactly the time the robot is talking, and cancelling it is the v1 "stop talking". Both guarantees are [audio.md](../audio/audio.md)'s ("`say` completes when the utterance has been heard, and exits silent"). **One `say` at a time, the newest wins:** a `say` called while one plays interrupts it — the running one flushed and raising `SpeechInterruptedError` in its caller — and plays ("Cancellation" above).
  - `play_sound(...)` — play a sound file / built-in sound (upstream `media.play_sound`).
- **Audio in (microphone)** — see [audio.md](../audio/audio.md)
  - `audio_input()` / `mic_sample_rate` — an async stream of the robot's **echo-cancelled** microphone PCM, for the caller to feed their **own** ASR. The bridge embeds no ASR engine and exposes no recognizer; it provides clean mic audio and manages the media session so echo cancellation applies. The stream is shaped to drop easily into common ASR engines (see [audio.md](../audio/audio.md)).
- **Audio-reactive motion (head wobbling)** — see [audio.md](../audio/audio.md) "Head wobbling"
  - `set_wobbling(enabled: bool)` — turn upstream's head wobbler on or off: while on, every sound the robot plays (`say`, `play_sound`, an emotion's sound) sways the head in time with its loudness, composed on top of whatever else the head is doing. Orchestration: dispatches to the upstream `enable_wobbling()` / `disable_wobbling()` (both halves — SDK-side and daemon-side). It is a **mode, not a move**: it holds until changed, and needs no motors — the daemon folds the offsets into the target pose whether or not torque is on, so enabling it on a resting robot is the natural "sway whenever you talk" declaration, visible once motors are `enabled` and audio plays. (Contrast the movement verbs, which fail fast without torque — see Motors below.)
  - `wobbling` (read-only `bool` property) — whether the bridge has wobbling on. Upstream exposes no getter, so this is the bridge's record of what it last set through `set_wobbling` or the config flag, not a daemon read; it is exact for the SDK-side wobbler that `say` drives. Readable at any time; `False` outside a session (entry turns it on by default).
  - **On by default: on at entry, off at exit.** The config's `motion.wobbling` flag ([config.md](config.md)) defaults to `true`, so `start()` enables wobbling right after the media session is up — every session's speech sways the head, whatever the synthesizer — and `wobbling: false` leaves the mode untouched (see Lifecycle above); and whenever `wobbling` is on at exit — from the flag or a later `set_wobbling(True)` — exit disables it before the robot disconnects, so the daemon-side switch (shared state across clients) is not left armed for the next app.
  - **Idle motion and tracking compose with it; emotions pause it.** Every idle move (breathing, the neutral hold, a custom one) and face tracking play with the sway added on top. `play_emotion` **pauses wobbling for the move** — one pause across consecutive emotions, from the first's start to the last's end — and restores it afterwards ([motion.md](../motion/motion.md) "Emotions through the loop"): a library emotion's own sound would otherwise drive audio-reactive motion on top of the choreographed trajectory, which reads as twitchy. Upstream's own wake/sleep emotes also quiesce it.
- **Presence & the idle move (background motion)** — see [motion.md](../motion/motion.md)
  - `set_presence(enabled: bool)` / `presence` (read-only `bool`) — whether the robot stays alive between verbs. On, the motion loop fills every idle moment with the idle move (breathing, a still neutral hold, or the caller's own); off, the bridge commands the head only while a verb runs and leaves it where the last move ended — for a caller driving the head through the raw robot. Emotions play either way.
  - `set_idle(mode: str)` / `idle` (read-only `str`) — which idle move presence plays: `"breathing"` (the built-in animation: slow breaths on the z axis with random rests between them, the head roaming in roll, pitch and yaw, and the antennas roaming and flicking independently outward from vertical), `"hold"` (the still hold at neutral) or `"custom"` (the caller's registered idle move; the hold while none is registered). Any other value raises `ValueError`.
  - `set_idle_move(factory)` / `idle_move` (read-only) — registers the custom idle move: a zero-argument callable returning a fresh `IdleMove` (a subclass itself, or a function), or `None` to clear it ([motion.md](../motion/motion.md) "Custom idle moves"). It is **accepted and stored whatever the idle mode is** and plays whenever the mode is `"custom"`, so the two verbs are called in either order and the move survives mode changes. With the mode `"custom"` and the robot idle it takes effect at once (a playing custom move fades out, the new one blends in). The factory is checked before it is stored — not callable, a call that raises, a result that is not an `IdleMove`, or an `offsets(0.0)` / `gaze_offsets(0.0)` that is not an `IdleOffsets` of finite numbers raises `ValueError` and leaves the registered move as it was. A move may override `gaze_offsets(t)` to say what it does while the head tracks a face ([motion.md](../motion/motion.md) "The gaze layer"); one that does not is still during gaze. `idle_move` reads the registered factory, or `None`.
  - All three are **modes** like wobbling and tracking: set initially by the config's `motion` block ([config.md](config.md) — presence on, idle `"breathing"`, no custom move), held until changed, needing no motors (the loop is paused without them). Changing one while idle transitions at once through a short blend (leaving a playing breathing or custom move eases the head to neutral first, presence off stops commanding at once); changing one during an emotion is recorded and applied when the emotion ends — an emotion is never interrupted to change idle behaviour; setting the current presence or idle value is a no-op. The three verbs need a running bridge (`BridgeError` otherwise, raised before anything is recorded — a failed call leaves the property at the config's value); outside a session the properties read the config's values, and exit resets them to it.
- **Perception (camera)** — see [camera.md](../vision/camera.md)
  - `camera` — the session's `CameraFeed`, the **one reader** of the robot's camera: `bridge.camera.latest()` is the newest `CameraFrame` — `frame_id`, `ts`, `image` as a numpy **BGR array** (`HxWx3`, `uint8`), `head_pose` — or `None` while no frame has arrived: before the session, after it, and wherever the daemon has no frame (no GL context, the headless sim on macOS — see [../docs/running-the-sim-daemon.md](../../docs/running-the-sim-daemon.md)). A property, not a verb: reading it is an instant, thread-safe sample of a latest-value slot, needs no motors, and any number of consumers — a display, an agent tool, the `custom` detection source, a vision graph plugged onto the feed — sample the same frames without taking them from one another, which two callers of upstream's one-shot `get_frame()` would. The frame's `image` is shared and read-only; a consumer that draws copies first. Encoding a frame for a model (base64/JPEG) is the caller's concern, not this layer's. Gaze-from-pixels (`look_at_image`) is still deferred.
- **Expression**
  - `play_emotion(name, ...)` — play a named recorded move from the emotions library (`RecordedMoves(...).get(name)`), with `list_emotions()` to enumerate. Backed by the upstream library and its HF-hub caching — see the Emotions library note below. Requires motors enabled (it moves the robot). **The move plays through the bridge's motion loop** ([motion.md](../motion/motion.md) "Emotions through the loop"), never through upstream's `async_play_move`: the loop is the one writer of the robot's target, and upstream's player is a second writer that would fight it. The verb resolves the move and queues it as a primary; primaries are exclusive and FIFO, so a second `play_emotion` waits its turn. The loop blends into the move's start pose, starts its sidecar sound (`media.play_sound`) as the trajectory starts, and plays it for `move.duration`. **Completes when the trajectory has played** — the sound started alongside it; the return to neutral that follows is the idle behaviour's, not the verb's (with presence on the head eases back and breathing resumes; with presence off it stays at the recording's end pose). Around the move — one pause across consecutive moves when several queue: taken when the first begins, released when the last in flight ends — the bridge **pauses wobbling and restores it on every exit path**, because the emotion's own sound would otherwise sway the head on top of the choreography; the motion loop itself leaves the gaze layer out of a primary and fades it back in afterwards ([motion.md](../motion/motion.md) "The gaze layer"), so an emotion plays as recorded whether or not a face is tracked. **Cancelling the task stops the emotion — motion and sound** (the "Cancellation" contract above): the loop drops the primary at its next tick — no longer commanding the trajectory, and stopping the move's sound through [audio.md](../audio/audio.md)'s `MediaSession.stop_sound()` (which also resets the head wobbler) when it had started it — and the verb re-raises once the loop has acknowledged the drop — silent at once, the session open, the idle move then blending in from where the cancel caught the head (presence on). The same stop runs when the move fails. The sound stop is the bridge's own machinery: upstream has no member that stops just a sound file — its `cancel_move()` takes the whole shared record + playback pipeline to `NULL`, which kills the media session's capture ([../docs/reachy-mini-api.md](../../docs/reachy-mini-api.md) "Cancelling a move").
- **Faces (perception)** — see [user_perception.md](../vision/user_perception.md)
  - `faces` (an `Observable[FaceReport]`, readable at any time) — the faces in front of the robot as the bridge's detection loop last saw them: `faces.value` is the current `FaceReport` (`faces` — normalised image coordinates, a pixel box and a `track_id` per face that stays the same while the same person stays in view, in `track_id` order — the camera `frame` the faces were found in, `ts`, `source`, `active`), and `async for report in faces.changes()` wakes on **a change in the number of faces** (debounced so a face the detector misses for a frame does not count as gone) and on `active` flipping — never on a face merely moving; `await faces.wait_for(lambda r: r.faces)` waits for someone to be there. `active=False` means no detector is looking (no detector configured, detection off, or no camera frame reaching it), not that nobody is there. The value outside a session is the inactive, empty report. Subscriptions are async iterators under the "Cancellation" contract: cancelling the awaiting task ends them promptly.
  - `set_face_detection(enabled: bool)` / `face_detection` (read-only `bool`) — whether the detection loop runs for the caller's sake. A **mode**, needing no motors (nothing moves). The loop also runs whenever head tracking is on, whatever this switch says (the tracker is its client), so turning detection off with tracking on changes nothing observable; `faces.value.active` reports what is actually running. Initial value: the config's `face_detection.enabled` (off by default). It needs a configured detector (`face_detection.detector`): with none, `set_face_detection(True)` raises `ValueError`.
  - `set_face_detector(factory)` / `face_detector` (read-only) — registers the custom detector for `face_detection.detector: "custom"`: a zero-argument callable returning an object with `detect(frame_bgr, ts) -> Sequence[PixelFace]`, or `None` to clear it ([user_perception.md](../vision/user_perception.md) "Custom detectors"). Checked before it is stored — callable, or `ValueError` with nothing changed; the detector itself is built when the loop starts; with the detector `custom` and the loop running, the loop restarts on the new detector, and clearing it then is refused (`ValueError`: stop tracking and detection first). Which detector runs is the config's `face_detection.detector` (`null` / `yunet` / `custom`, [user_perception.md](../vision/user_perception.md) "Detectors"), not a verb.
- **Attention / gaze (autonomous)** — see [head_tracking.md](../motion/head_tracking.md)
  - `start_head_tracking(*, focus: bool = False)` / `stop_head_tracking()` — the bridge's **own head tracker**: the robot autonomously keeps the tracked face in view. The tracker follows one of the faces the detection loop reports — the biggest at first, held while it is seen, the head waiting toward its last position for a while before switching to the biggest other face ([head_tracking.md](../motion/head_tracking.md) "Whom the head follows") — aims it and hands that aim to the motion loop, which composes it into the idle move ([motion.md](../motion/motion.md) "The gaze layer") — the head looks at the face and does what the idle move's `gaze_offsets` says around that direction (breathing keeps breathing with its roaming toned down; a custom move that defines none is still). With **`focus=True`** the head holds exactly on the face instead: the idle move's head motion is left out, its antennas kept; calling the verb again with the other value switches between the two (the change fades over `BLEND_S`). No blend weight: the daemon's tracker had one because it blended its aim with the client's target; the bridge's gaze layer is always the aim in full, and the idle move's own gaze-time motion is what varies. The daemon's own tracking is never touched: the bridge neither arms nor stops it ([robot.md](robot.md)). A **mode, not a move**, like `set_presence`: it holds until changed, needs **no motors** (the motion loop is paused without them and emits nothing with presence off, so the aim simply has no effect until they are on) and raises nothing about them. It needs a configured detector — with `face_detection.detector` `null` it raises `ValueError` — and starting it starts the detection loop if it is not already running.
  - `head_tracking` (an `Observable[HeadTrackingReport]`, readable at any time) — the tracker's state ([head_tracking.md](../motion/head_tracking.md) "The head tracking report"): `active`, `focus`, `attention`, and the `track_id` of the face the head follows — the link between the face report's faces and the head. `changes()` wakes when tracking starts or stops, focus switches, attention changes, or the head passes to another person; never on a face moving. Outside a session, the inactive report. Subscriptions follow the "Cancellation" contract.
  - `tracking` (read-only `bool` property) — whether the bridge's tracker is on: the bridge's own record. Set by `start_head_tracking`, cleared by `stop_head_tracking`; outside a session reads the config's value. `tracking_focus` (read-only `bool`) — whether it holds the head on the face (`focus`); `False` while tracking is off and outside a session.
  - **Attention — the head is handed back when nobody is there.** The face owns the head only *while someone is being tracked*; alone, the robot idles in full (it breathes, [motion.md](../motion/motion.md)). Since the bridge owns the aim this is the tracker's own behaviour: when the followed face has been missing for `TRACKING_LOST_S` (2 s, [head_tracking.md](../motion/head_tracking.md)) with nobody large enough to switch to, it withdraws the aim and the motion loop fades the gaze layer out, easing the head onto the idle move; the next face brings the aim back and the layer fades in. `attention` (read-only `str | None` property) is **derived** from that state: `"engaged"` while the tracker holds an aim, `"watching"` while tracking is on and nobody has been seen for longer than the loss timeout, `None` when tracking is off. There is no attention loop, no daemon weight to dance, and no re-anchor — the loop composes the layer itself, so its stream never drifts from the head.
  - **One line of config away.** Tracking starts at session entry when the config's `motion.tracking` flag is on ([config.md](config.md); off by default, since it needs a detector the default config does not name — the example config names `yunet` and turns it on): the tracker starts with the detection loop, whether or not motors are enabled — its aim takes effect the moment the motion loop resumes. `stop_head_tracking()` turns it off until `start_head_tracking(...)` is called again. At exit the tracker stops with the detection loop.
- **Motors / torque**
  - `set_motors_state(state)` — caller-facing torque control through a single verb taking `"enabled"` / `"disabled"` / `"gravity_compensation"`, **decoupled from the connection**: staying connected does not mean staying energized, so a caller can rest the motors while still talking/listening, then re-engage for motion. It also drives the motion loop ([motion.md](../motion/motion.md) "Motors"): `"enabled"` resumes it (re-anchored on the present pose, so the head eases into the idle move rather than snapping) and the tracker's aim, if one is held, is composed in from there (tracking itself needs no motors, see "Attention / gaze" above); the two resting states pause the loop only. `"gravity_compensation"` is a *gentle* rest — the head holds its position instead of drooping — versus `"disabled"` (torque off, limp). The bridge does **not** set a state on connect and does **not** auto-toggle around individual moves (that would trip the upstream `enable_motors()` "pins to the present pose" gotcha and add a click/settle per move); the state, once set, holds until the caller changes it. Orchestration: the one verb dispatches to the matching upstream primitive (`enable_motors` / `disable_motors` / `enable_gravity_compensation`). **Gravity compensation needs the daemon's Placo kinematics engine** (`reachy-mini[placo_kinematics]`, daemon started with `--kinematics-engine Placo`) — a requirement on the *daemon*, not on the caller's environment. Upstream sends the mode fire-and-forget; a robot daemon on another engine rejects it and closes the client's connection, so the call itself returns normally and every *later* robot call fails (`TimeoutError` / `ConnectionError`) with no way to reconnect. The bridge therefore **checks before sending**: `set_motors_state("gravity_compensation")` reads the daemon status and, unless it reports a simulation (`simulation_enabled` / `mockup_sim_enabled` — the sim daemon ignores motor modes, so the command is sent as before), reads the engine from the daemon's `GET /api/kinematics/info`. When the engine is not `Placo`, or cannot be read, it raises `GravityCompensationUnsupportedError` (a `BridgeError`) naming the engine and the fix, sends nothing, and the connection and the motor state are untouched. The check runs on every call (one status read + one HTTP request; no cache that could go stale across a daemon restart). The `fake` reports its engine through its daemon client stand-in (`Placo` by default), so the refusal is exercisable offline. The testing harness probes the same engine read as the `gravity_compensation` capability ([testing.md](../testing/testing.md)).
  - `get_motors_state()` — read the current state (same three values) so a caller can check **before** calling a movement verb, rather than discovering it via the fail-fast error. Returns the daemon's `motor_control_mode` in JSON-friendly form; "ready to move" is `state == "enabled"`. The daemon status reflects a `set_motors_state` a fraction of a second later (about 0.2 s on hardware), so a read made immediately after a set can still return the previous state; a caller confirming a switch polls briefly.
  - **Hardware honors the state; the sim does not.** On a Reachy Mini Lite over USB (`reachy_mini` 1.10, default kinematics engine) `"disabled"` and `"enabled"` each read back as set, and the head goes limp or holds accordingly. The MuJoCo sim daemon ignores every motor-state change and keeps reporting `"enabled"` (headless and viewer alike). The live tier therefore asserts read + dispatch (a valid mode) on every target, and the exact dispatch→state mapping is pinned on the `fake` (`tests-e2e/test_bridge.py::test_motor_state_reads_and_dispatches_over_the_live_path`, which lowers the head to the SDK's sleep pose before torque goes off on hardware).

**Motor torque is an explicit precondition, enforced by fail-fast — not auto-managed.** The audio verbs (`say`, `audio_input`, `play_sound`), the modes (`set_wobbling`, `set_presence`, `set_idle`, `set_face_detection`, `start_head_tracking` — tracking moves the head only through the motion loop, which is paused without motors) and the perception verbs need no motors. `play_emotion` **moves the robot**, so it requires torque `Enabled`; if it isn't, it **raises `MotorsNotEnabledError`** rather than silently enabling motors or sending a command that does nothing. This is observable, not guessed: the daemon reports `motor_control_mode` ∈ `Enabled` / `Disabled` / `GravityCompensation` via the daemon client (`robot.client.get_status().backend_status` — the public `ReachyMini` has no motor-mode getter, so the bridge reads it the way the SDK itself does), so a verb reads the *actual* state before acting. Reading rather than assuming is essential because the motor state is owned by the **daemon's** wake/sleep lifecycle, not by connecting: with `wake_up_on_start` (the sim/local daemon default) the daemon's boot sequence **enables** the motors just before the wake-up emote — so a freshly-started daemon reads `Enabled` — and `goto_sleep` (on stop, or an idle timeout) **disables** them again; a wireless robot instead boots asleep. Connecting (`__enter__`) itself changes nothing, so the bridge adds no auto-enable and needs no `is_awake` notion of its own — torque is a separate, observable, caller-owned concern (upstream details in [../docs/reachy-mini-api.md](../../docs/reachy-mini-api.md)).

**Emotions library — delegated to the SDK, not re-implemented.** `play_emotion` / `list_emotions` wrap the upstream `reachy_mini.motion.recorded_move.RecordedMoves`, defaulting to its `DEFAULT_EMOTIONS_DATASET` (`pollen-robotics/reachy-mini-emotions-library`). Loading and caching are the SDK's: `RecordedMoves` resolves from the standard Hugging Face hub cache **offline-first** (`snapshot_download(..., local_files_only=True)`), falling back to a network download only on a cache miss — so the bridge keeps **no cache of its own**. Two things the implementation must honor: (1) constructing `RecordedMoves` does blocking disk/network IO, so the bridge builds it **lazily, once per connection** (cached instance, never at import) and off the event loop via `asyncio.to_thread` — and cancel-safe: a `list_emotions` / `play_emotion` cancelled during that first load does not discard it (the load is shielded, finishes in its thread, and the next call awaits the same in-flight load rather than starting a second download); (2) on a real/sim robot the daemon **preloads** the default datasets at startup, so the first call is normally a cache hit — on the `fake`/offline path the emotions library is stubbed (no HF access), consistent with [audio.md](../audio/audio.md)'s fake media. v1 keeps `play_emotion(name)` **literal** (name in → move played); the conversation app's compact-intent→move resolution and curated random-fallback pool are a caller/agent concern, not part of the bridge.

### Deferred to post-v1

Named here so the boundary is explicit; each is a straightforward addition once v1 lands:

- **Manual movement & gaze:** `look_at(...)` (image-pixel `look_at_image` / 3D-world `look_at_world` dispatch), `set_head_pose(roll, pitch, yaw, duration, ...)`, and composed gestures `nod(...)` / `shake_head(...)` / `turn(yaw, ...)`. These are what makes open question 1 (frame/units conventions) load-bearing — so that question is a **post-v1** concern. When they land they are primaries of the motion loop ([motion.md](../motion/motion.md)), not calls to upstream's `goto_target` (a daemon-side move, during which the daemon drops the loop's targets).
- **`wake()` / `sleep()`** — the upstream `wake_up()` / `goto_sleep()` personality emotes. Optional session bookends; not a prerequisite for anything (see torque note above). Both are daemon-side moves, so they pause the motion loop for their duration when they land.
- **`set_antennas(left, right, ...)`** — direct antenna control in degrees.
- **Rich perception:** `get_head_pose()`, `get_imu()`, and sound direction of arrival (`get_sound_direction()` / DoA). Their return shapes settle with this batch (see open questions). The camera (`camera`, [camera.md](../vision/camera.md)) and the faces (`faces`, [user_perception.md](../vision/user_perception.md)) are **no longer deferred** — they are in scope above; the bridge serves an agent that can hear, speak, see who is there and follow them, and read a camera frame, but still can't gaze from a pixel (`look_at_image`, above) or read pose/IMU/DoA.
- **`stop_talking()` — barge-in from outside the `say` task.** Cancelling the `say` task is the v1 stop, and a real one: `say` flushes the queued speaker audio (`media.audio.clear_player()`) and resets the wobbler before re-raising, so speech ends within the sink's buffer ([audio.md](../audio/audio.md)). What stays deferred is a verb that stops speech for a caller who does *not* hold the task (e.g. an agent runtime's tool call): it needs the bridge to track its in-flight `say` task so `stop_talking()` can cancel it — a flush alone would let the still-running `say` push the rest of the utterance.

### Orchestration is the point

Verbs that don't map 1:1 to an upstream call are where this layer earns its keep. In v1 that's `play_emotion` resolving a name to a recorded move, checking torque first so the move actually plays (failing fast otherwise), playing it through the motion loop, and pausing wobbling around it; the presence / idle modes over that loop, including a caller's own idle move; and the faces — a detection loop feeding an observable report and the bridge's own head tracker over the same loop ([user_perception.md](../vision/user_perception.md)). The richer orchestration — `look_at` choosing the right upstream helper, `nod`/`shake_head` sequencing poses — arrives with the deferred movement verbs. Pure pass-throughs (e.g. `play_sound`, `set_wobbling`, and later `get_imu`) are thin by design.

## Open questions

1. **Frame/units conventions (post-v1).** Exact axes, origin, and angle conventions for the deferred manual gaze/pose verbs (`look_at` / `set_head_pose`), so callers agree (upstream world frame: x forward, y left, z up). Settles when those verbs land.
2. **Perception return shapes (post-v1).** Return types for the *remaining* deferred perception verbs (`get_head_pose` / `get_imu` / DoA).
3. **A stop for `play_sound`.** `play_sound` returns once the file has started, so the sound outlives the call with no way to stop it — the one verb outside the "Cancellation" contract's two classes. Either it becomes a spanning verb (completes when the sound has been heard, cancel stops it — needs the file's end, from the local `playbin`'s duration/EOS or by decoding the file) or it gains a `stop_sound()` counterpart on [audio.md](../audio/audio.md)'s `MediaSession.stop_sound()`. Deferred until a caller needs it; the primitive exists either way.
