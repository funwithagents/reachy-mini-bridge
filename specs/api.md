# Interaction API (`ReachyMiniApi`)

**Status:** Updated

## Purpose

`ReachyMiniApi` is the high-level, intention-level surface for driving the robot. Where the upstream SDK speaks in 4x4 pose matrices and radians, `ReachyMiniApi` speaks in **human intent and human units**: "look at this point", "nod", "play the happy emotion", "say this", in degrees / seconds / named emotions. It orchestrates the lower-level [robot.md](robot.md) primitives (the motion loop's target stream — [motion.md](motion.md) — recorded moves, and media) into single semantic verbs.

It is the layer a human, service, or agent codes against directly, and the layer [tools.md](tools.md) wraps for LLM/agent use. **Action verbs** take and return plain, JSON-friendly Python values so they compose cleanly into tools. **Perception verbs return the natural rich object** instead — a camera frame is a numpy BGR array, the mic is a raw-PCM stream ([audio.md](audio.md)) — because that's what a Python caller wants to work with; the JSON/base64 encoding for a model is [tools.md](tools.md)'s job, done once at that boundary.

### Async-native

`ReachyMiniApi` is **async-native**. Audio forces it (see [audio.md](audio.md)): speech synthesis is `async`, and a **live microphone stream** runs concurrently with playback and with the robot moving — full-duplex interaction (a caller's ASR consuming the mic while `say` speaks, plus barge-in) keeps both audio paths on one event loop.

- The upstream SDK's **blocking** calls (`enable_motors`, `get_status`, …) run under `asyncio.to_thread(...)`, and the 60 Hz target stream runs on its own thread ([motion.md](motion.md)), so motion never stalls the audio loops.
- The upstream `ReachyMini` is **synchronous** and mirrors the SDK 1:1; this layer is where async lives.
- A consuming agent runtime that needs **sync** tool callables gets the sync↔async bridging at the [tools.md](tools.md) layer (a managed background loop).

### Cancellation — every async verb is fully cancellable

Cancelling the task that awaits a verb — `task.cancel()`, an `asyncio.timeout`, a `TaskGroup` unwinding — is the bridge's one interruption mechanism, so every `async` verb honors it fully. **"Fully cancellable" means three things, all required:**

1. **The cancel returns promptly.** The `CancelledError` reaches the caller at the verb's next `await`; a verb never swallows it and never holds the cancel until what it was doing would have ended on its own. The bound is one loop tick or one short SDK call: a blocking SDK call already running under `asyncio.to_thread` cannot be interrupted, so it finishes in its thread (a fraction of a second for every call the bridge makes this way) while the cancel propagates at once.
2. **The effect stops with the verb.** Whatever the verb was producing over time stops *before* the `CancelledError` propagates: queued speaker audio is flushed, a playing sound file is stopped, a trajectory is no longer commanded, the head wobbler is reset. The verb stops exactly what it started.
3. **The robot and the session stay usable.** A cancel undoes only the verb's own in-flight effect. Modes the verb did not set — `wobbling`, head tracking, the motor state — are left exactly as they were, the media session stays open, and the next verb works immediately: a cancelled `say` or `play_emotion` can be followed by another in the same breath.

What it does **not** mean: **no rewind.** An effect already delivered stays delivered — sound already heard was heard, and a cancelled move does not return the head to its starting pose. What the head does next is the presence behaviour's business, not the verb's ([motion.md](motion.md)): with presence on, the idle move blends in from wherever the cancel caught the head, exactly as after a completed emotion; with presence off the head stays there. Nor does a verb stop *another* verb's effect; the deferred `stop_talking()` (below) is the one planned exception, for a caller who does not hold the `say` task.

Verbs fall in two classes. **Spanning verbs** run for as long as their effect — `say`, `play_emotion`, the `audio_input` stream, and the session bring-up `__aenter__` — and are where the three guarantees do real work; each has a test on the `fake` that cancels it mid-flight and asserts the effect stopped and the session still works, which is why the fake keeps real timing for them ([robot.md](robot.md)). **Instant verbs** — `set_motors_state`, `get_motors_state`, `start_head_tracking` / `stop_head_tracking`, `set_wobbling`, `set_presence` / `set_breathing`, `get_camera_frame`, `list_emotions` — hand one short command to the SDK (or the motion loop) and return; a cancel returns promptly and the command completes in its thread. Their effect, when it outlives the call, is a *mode* switched off by its counterpart verb, not something a cancel unwinds. `play_sound` is today an instant verb whose effect (a sound file playing to its end) has no counterpart — open question 3.

## Core concepts / Decided

- **Constructed from a config.** `ReachyMiniApi(config: ReachyMiniConfig | str = "real", *, synthesizer: SpeechSynthesizer | None = None)` takes a [config.md](config.md) `ReachyMiniConfig` — backend, upstream connection options, daemon management, default synthesizer, audio profile — and builds the robot internally (see [robot.md](robot.md)): the real `reachy_mini.ReachyMini` for `real`/`sim`, our `FakeReachyMini` for `fake`, so the Api is fully unit-testable on the `fake` backend. A bare backend string is shorthand for `ReachyMiniConfig(backend=...)`, so `ReachyMiniApi("fake")` is the one-liner. The `from_dict(data, **kw)` / `from_json(text, **kw)` / `from_json_file(path, **kw)` classmethods mirror the config's constructor trio and build the api in one call — a host application's config file, JSON string, or dict yields a talking robot directly. The explicit `synthesizer=` keyword wins over the config's `tts` block, which is then not consumed; with neither, `say` raises `BridgeError` (see [audio.md](audio.md)). A `tts` block whose adapter build fails degrades to no voice rather than failing construction: every exception from building the adapter — tts-engine's `ConfigError` for a provider whose extra is not installed or a bad block, an unset key, a model that fails to load — is caught and recorded on the read-only `synthesizer_error: Exception | None` property (`None` when the voice built, when an explicit `synthesizer=` was passed, or when there is no `tts` block) and logged at `WARNING`. The api still comes up with no voice; `say` then raises `BridgeError` chained (`from`) to the recorded cause, its message naming it. The policy stays the host's: a host that wants hard failure checks `synthesizer_error` after construction and raises. A test asserts on the fake by reaching it back through `api.robot` (the escape hatch), not by injecting one.
- **Front door.** `from reachy_mini_bridge import ReachyMiniApi` is the entry point: the package root re-exports exactly what a caller needs to drive the robot — `ReachyMiniApi`, `ReachyMiniConfig`, the `SpeechSynthesizer` contract and its shipped `TTSEngineSynthesizer` adapter, and the `BridgeError` / `MotorsNotEnabledError` / `GravityCompensationUnsupportedError` / `ConfigError` errors a caller catches. Everything else (`MediaSession`, the conversion helpers, `FakeReachyMini`, `build_robot`, `AnyReachyMini`, `DaemonError`) is imported from its own module. The imports are eager: `reachy_mini` is a base dependency, and `TTSEngineSynthesizer` imports `tts_engine` only in its constructor, so the front door pulls in no extra.
- **Lifecycle.** Construction stores the config and nothing else runs — no daemon, no connection. `async with ReachyMiniApi(...)` brings everything up in order: the managed daemon when `daemon.spawn` is not `"never"` (the MuJoCo daemon for `sim`, a USB-attached robot's hardware daemon for `real`; entered off the event loop via `asyncio.to_thread`, see [daemon.md](daemon.md)), then the robot (built with `build_robot(backend, **robot)` and entered — upstream's `ReachyMini` connects in its constructor, so it is built only once the daemon is ready), then the media session, then head wobbling unless the config's `motion.wobbling` flag turns it off (`set_wobbling(True)`, see "Audio-reactive motion" below), then the motion session ([motion.md](motion.md)) — the loop thread that owns `set_target`, started with the config's `motion.presence` / `motion.breathing` switches and paused unless the motors read `enabled`; when they do, the loop resumes and, if `motion.tracking` is on, face tracking is armed too (see "Attention / gaze" below). A failure at any step unwinds what already started; exit stops the motion session first (easing the head to neutral when presence is on and the loop is commanding), then disables wobbling and stops face tracking whenever either is on, then tears down the media session, then the robot, then an owned daemon, each even when another fails (an `AsyncExitStack` holds the steps). `api.robot` / `api.raw` are available only while entered and raise `BridgeError` otherwise, since there is no robot object before the connection is made. **Bring-up is cancellable** (see "Cancellation" above): a cancel during `__aenter__` — an `asyncio.timeout` around the `async with`, say — is handled like a failure. The step in flight (a daemon spawn, the robot connect, a media `start_*`) cannot be interrupted in its thread, so it is allowed to finish, then everything started so far is torn down, then the `CancelledError` propagates — nothing is leaked, at the cost of the cancel taking as long as that step (up to `daemon.startup_timeout` for a spawn).
- **Raw access preserved.** The underlying robot object stays reachable through the Api as `api.robot` (a.k.a. `api.raw`) so nothing is a dead end — for `real`/`sim` it *is* the full native `ReachyMini`.
- **Human units.** Angles in **degrees**, durations in **seconds**, positions in a documented frame. The Api converts to the upstream's matrices/radians internally (via `reachy_mini.utils.create_head_pose` and friends).
- **Idempotent, forgiving verbs.** Methods validate/clamp to safe ranges and fail with clear `ValueError`s rather than sending bad poses downstream.
- **Errors.** Out-of-range or unknown input raises `ValueError`. Errors from the bridge's own logic derive from `BridgeError(RuntimeError)` in `errors.py`: `MotorsNotEnabledError` is the *state* error a movement verb raises when torque is not `enabled` (see Motors), `GravityCompensationUnsupportedError` its sibling for a daemon that cannot hold that mode, and `DaemonError` covers the managed daemon ([daemon.md](daemon.md)). `ConfigError` subclasses `ValueError`, since a malformed config is bad input ([config.md](config.md)). Connection errors are upstream `reachy_mini`'s, surfaced unwrapped.

### v1 scope — the minimum for interaction

v1 is deliberately narrow: the smallest verb set that makes the robot a **conversational, face-following** presence — **talk, listen, express, follow the person it's talking to, and stay visibly alive in between** (breathing, [motion.md](motion.md)). Manual movement/gaze and rich perception are explicitly **deferred to post-v1** (see below).

**In scope for v1:**

- **Audio out** — see [audio.md](audio.md)
  - `say(text, ...)` — synthesize speech via a **pluggable** `SpeechSynthesizer` ([audio.md](audio.md)); the default adapter wraps our first-party [`tts-engine`](../../tts-engine) (a base dependency; the provider comes from a `tts-pocket` / `tts-elevenlabs` extra), but callers can supply any synthesizer. On a real/sim robot the audio is routed through the robot speaker (required for echo cancellation), not the local device. `say` **completes when the utterance has finished playing** on the speaker (not when it has merely been queued), and **cancelling the `say` task stops the speech** — the queued audio is flushed and the head wobbler reset — so `await api.say(...)` spans exactly the time the robot is talking, and cancelling it is the v1 "stop talking". Both guarantees are [audio.md](audio.md)'s ("`say` completes when the utterance has been heard, and exits silent").
  - `play_sound(...)` — play a sound file / built-in sound (upstream `media.play_sound`).
- **Audio in (microphone)** — see [audio.md](audio.md)
  - `audio_input()` / `mic_sample_rate` — an async stream of the robot's **echo-cancelled** microphone PCM, for the caller to feed their **own** ASR. The bridge embeds no ASR engine and exposes no recognizer; it provides clean mic audio and manages the media session so echo cancellation applies. The stream is shaped to drop easily into common ASR engines (see [audio.md](audio.md)).
- **Audio-reactive motion (head wobbling)** — see [audio.md](audio.md) "Head wobbling"
  - `set_wobbling(enabled: bool)` — turn upstream's head wobbler on or off: while on, every sound the robot plays (`say`, `play_sound`, an emotion's sound) sways the head in time with its loudness, composed on top of whatever else the head is doing. Orchestration: dispatches to the upstream `enable_wobbling()` / `disable_wobbling()` (both halves — SDK-side and daemon-side). It is a **mode, not a move**: it holds until changed, and needs no motors — the daemon folds the offsets into the target pose whether or not torque is on, so enabling it on a resting robot is the natural "sway whenever you talk" declaration, visible once motors are `enabled` and audio plays. (Contrast the movement verbs, which fail fast without torque — see Motors below.)
  - `wobbling` (read-only `bool` property) — whether the bridge has wobbling on. Upstream exposes no getter, so this is the bridge's record of what it last set through `set_wobbling` or the config flag, not a daemon read; it is exact for the SDK-side wobbler that `say` drives. Readable at any time; `False` outside a session (entry turns it on by default).
  - **On by default: on at entry, off at exit.** The config's `motion.wobbling` flag ([config.md](config.md)) defaults to `true`, so `async with` enables wobbling right after the media session is up — every session's speech sways the head, whatever the synthesizer — and `wobbling: false` leaves the mode untouched (see Lifecycle above); and whenever `wobbling` is on at exit — from the flag or a later `set_wobbling(True)` — exit disables it before the robot disconnects, so the daemon-side switch (shared state across clients) is not left armed for the next app.
  - **Idle motion and tracking compose with it; emotions pause it.** Breathing, the neutral hold and face tracking all play with the sway added on top. `play_emotion` **pauses wobbling for the move** and restores it afterwards ([motion.md](motion.md) "Emotions through the loop"): a library emotion's own sound would otherwise drive audio-reactive motion on top of the choreographed trajectory, which reads as twitchy. Upstream's own wake/sleep emotes also quiesce it.
- **Presence & breathing (background motion)** — see [motion.md](motion.md)
  - `set_presence(enabled: bool)` / `presence` (read-only `bool`) — whether the robot stays alive between verbs. On, the motion loop fills every idle moment with the idle move (breathing, or a still neutral hold); off, the bridge commands the head only while a verb runs and leaves it where the last move ended — for a caller driving the head through the raw robot. Emotions play either way.
  - `set_breathing(enabled: bool)` / `breathing` (read-only `bool`) — which idle move presence plays: breathing (slow breaths on the z axis with random rests between them, the head roaming in roll, pitch and yaw, and the antennas roaming and flicking independently outward from vertical) or the still hold at neutral.
  - Both are **modes** like wobbling and tracking: on by default from the config's `motion` block ([config.md](config.md)), held until changed, needing no motors (the loop is paused without them). Toggling while idle transitions at once through a short blend (turning breathing off eases the head to neutral, presence off stops commanding at once); toggling during an emotion is recorded and applied when the emotion ends — an emotion is never interrupted to change idle behaviour; setting the current value is a no-op. Outside a session both properties read the config's values.
- **Perception (camera)**
  - `get_camera_frame()` — grab the latest camera frame as a numpy **BGR array** (`HxWx3`, `uint8`), or `None` when none is available yet. A thin pass-through of the upstream `media.get_frame()` run off the event loop, mirroring its behavior exactly: the daemon returns `None` until a frame is buffered and wherever there is no GL context (the headless sim on macOS — see [../docs/running-the-sim-daemon.md](../docs/running-the-sim-daemon.md)), so this verb does too rather than raising. Needs no motors (read-only). This is the one perception verb v1 ships; the rest stay deferred (below). The base64/JPEG encoding for a model is [tools.md](tools.md)'s concern, not this layer's. v1 no longer ships a fully "blind" agent — it can read a frame, though gaze-from-pixels (`look_at_image`) is still deferred.
- **Expression**
  - `play_emotion(name, ...)` — play a named recorded move from the emotions library (`RecordedMoves(...).get(name)`), with `list_emotions()` to enumerate. Backed by the upstream library and its HF-hub caching — see the Emotions library note below. Requires motors enabled (it moves the robot). **The move plays through the bridge's motion loop** ([motion.md](motion.md) "Emotions through the loop"), never through upstream's `async_play_move`: the loop is the one writer of the robot's target, and upstream's player is a second writer that would fight it. The verb resolves the move and queues it as a primary; primaries are exclusive and FIFO, so a second `play_emotion` waits its turn. The loop blends into the move's start pose, starts its sidecar sound (`media.play_sound`) as the trajectory starts, and plays it for `move.duration`. **Completes when the trajectory has played** — the sound started alongside it; the return to neutral that follows is the idle behaviour's, not the verb's (with presence on the head eases back and breathing resumes; with presence off it stays at the recording's end pose). Around the move the api **pauses face tracking (weight 0) and wobbling, and restores both on every exit path** (tracking to the attention state's current daemon weight, see "Attention" below), because at full tracking weight the daemon discards the head target (the emotion would not show) and because the emotion's own sound would otherwise sway the head on top of the choreography. **Cancelling the task stops the emotion — motion and sound** (the "Cancellation" contract above): the loop stops commanding the trajectory at its next tick, and the bridge stops the move's sound through [audio.md](audio.md)'s `MediaSession.stop_sound()` (which also resets the head wobbler) before re-raising — silent at once, the session open, the idle move then blending in from where the cancel caught the head (presence on). The same stop runs when the move fails. The sound stop is the bridge's own machinery: upstream has no member that stops just a sound file — its `cancel_move()` takes the whole shared record + playback pipeline to `NULL`, which kills the media session's capture ([../docs/reachy-mini-api.md](../docs/reachy-mini-api.md) "Cancelling a move").
- **Attention / gaze (autonomous)**
  - `start_head_tracking(weight: float = 1.0)` / `stop_head_tracking()` — wrap the daemon-side face tracker (upstream `start_head_tracking(weight=...)` / `stop_head_tracking()`). The robot **autonomously** keeps a detected face centered; this is *not* a manual control loop the bridge runs. The daemon blends the face aim into whatever target the motion loop sends by the weight — at `1.0` the face owns the head (the daemon ignores the head target; only the antennas still breathe), lower weights let the idle motion show through. The api **keeps the weight it last requested** (its own record, as for wobbling; cleared by `stop_head_tracking`) so `play_emotion` can dip it to `0` for a move and restore it. The daemon's face target (`get_tracked_face()`) is read by the attention loop below; exposing it as a perception verb stays deferred. **Requires motors enabled** (see Motors below): calling it directly raises `MotorsNotEnabledError` otherwise.
  - `tracking` (read-only `bool` property) — whether the bridge wants tracking on: the api's own record (as for `wobbling`), not a daemon read. Set by `start_head_tracking`, cleared by `stop_head_tracking`; outside a session reads the config's value.
  - **Attention — the head is handed back when nobody is there.** The face owns the head only *while someone is being tracked*; alone, the robot idles in full (it breathes, [motion.md](motion.md)). This is the bridge's doing, because the daemon does not hand the head back on its own (SDK 1.10, [../docs/reachy-mini-api.md](../docs/reachy-mini-api.md) "Face tracking"): it applies the requested weight only at a face detection (until the first one the loop's target flows and the head breathes); once applied at `1.0`, the head component of every target is discarded; on a face loss it recentres the head to neutral after 2 s but **keeps discarding** — the head then sits dead at neutral while the antennas breathe. Only a request at weight `0` clears that, and weight `0` also pauses the detector. So whenever tracking is active the api runs an **attention loop** — an asyncio task polling the daemon's latest face target (`robot.get_tracked_face(wait=False)`, the last status message received; no round trip) every `ATTENTION_POLL_S = 0.2` s — with two states, readable as the `attention` property (`"engaged"` / `"watching"`; `None` when tracking is not active):
    - **engaged** — a face was reported within the last `ATTENTION_GRACE_S = 3.0` s: the caller's requested weight is on the daemon. Tracking starts engaged (the daemon's own weight is `0` until it sees a face, so a fresh start breathes and engages at first sight).
    - **watching** — no face for the grace period: the api asks the motion loop to **re-anchor** ([motion.md](motion.md) "Re-anchor on request") and, once it has, re-arms tracking through weight `0` and then `ATTENTION_WATCH_WEIGHT = 0.05`. The `0` clears the daemon's aim and weight; the small weight keeps the detector running while letting the loop's target through (the daemon has no aim to pull toward until a face appears). The grace period exceeds the daemon's 2 s recentre, so the head is at neutral when it is handed back, and the re-anchor makes the loop resume from that present pose rather than from wherever its discarded stream had got to — no jump.
    - **watching → engaged** on the first poll reporting a face: the requested weight is re-sent; the daemon applies it at its next detection (a frame later; its aim starts from the current head pose and eases toward the face, so engagement is smooth on its side).
    - Every tracking send — the verbs, `play_emotion`'s dip and restore, the attention transitions — goes through one asyncio lock, and the loop makes no transition while a `play_emotion` is in flight, so a transition never lands inside a move; `play_emotion`'s restore sends the state's *current* daemon weight (the requested weight when engaged, the watch weight otherwise). `start_head_tracking(weight)` records the weight and (re)starts engaged; `stop_head_tracking()` and exit stop the attention loop together with the tracker. A status read that fails is logged and skipped, never fatal. The three values are module constants of `api.py`, not config (a knob would land in the `motion` block, [config.md](config.md)). A daemon-side fix — hand the head back on sustained loss — would make most of this unnecessary.
  - **On by default, realized whenever motors allow it.** Like `wobbling`, tracking is on by default from the config's `motion.tracking` flag ([config.md](config.md)). Unlike `wobbling`, it needs motors to actually engage — so the default is a *desire*, not an immediate action: at session entry it starts at once only if motors already read `enabled`; otherwise it stays pending and the next `set_motors_state("enabled")` starts it (re-using the same motor-state read `set_motors_state` already does, not a second poll — see Motors below on why that matters). `stop_head_tracking()` cancels the desire until `start_head_tracking(...)` is called again, so a caller's explicit "off" is never silently re-armed by a later motor-enable. Whenever tracking is still on at exit — from the flag or a later `start_head_tracking` — exit stops it before the robot disconnects, so the daemon-side switch is not left armed for the next app (mirroring `wobbling`'s exit behaviour).
- **Motors / torque**
  - `set_motors_state(state)` — caller-facing torque control through a single verb taking `"enabled"` / `"disabled"` / `"gravity_compensation"`, **decoupled from the connection**: staying connected does not mean staying energized, so a caller can rest the motors while still talking/listening, then re-engage for motion. It also drives the motion loop ([motion.md](motion.md) "Motors"): `"enabled"` resumes it (re-anchored on the present pose, so the head eases into the idle move rather than snapping) and, when tracking is wanted but not yet active (the config default, or a `start_head_tracking` call made while motors weren't enabled), arms it too — without a second motor-state read, since this call has just confirmed the state itself (see "Attention / gaze" above); the two resting states pause the loop only. `"gravity_compensation"` is a *gentle* rest — the head holds its position instead of drooping — versus `"disabled"` (torque off, limp). The bridge does **not** set a state on connect and does **not** auto-toggle around individual moves (that would trip the upstream `enable_motors()` "pins to the present pose" gotcha and add a click/settle per move); the state, once set, holds until the caller changes it. Orchestration: the one verb dispatches to the matching upstream primitive (`enable_motors` / `disable_motors` / `enable_gravity_compensation`). **Gravity compensation needs the daemon's Placo kinematics engine** (`reachy-mini[placo_kinematics]`, daemon started with `--kinematics-engine Placo`) — a requirement on the *daemon*, not on the caller's environment. Upstream sends the mode fire-and-forget; a robot daemon on another engine rejects it and closes the client's connection, so the call itself returns normally and every *later* robot call fails (`TimeoutError` / `ConnectionError`) with no way to reconnect. The bridge therefore **checks before sending**: `set_motors_state("gravity_compensation")` reads the daemon status and, unless it reports a simulation (`simulation_enabled` / `mockup_sim_enabled` — the sim daemon ignores motor modes, so the command is sent as before), reads the engine from the daemon's `GET /api/kinematics/info`. When the engine is not `Placo`, or cannot be read, it raises `GravityCompensationUnsupportedError` (a `BridgeError`) naming the engine and the fix, sends nothing, and the connection and the motor state are untouched. The check runs on every call (one status read + one HTTP request; no cache that could go stale across a daemon restart). The `fake` reports its engine through its daemon client stand-in (`Placo` by default), so the refusal is exercisable offline. The testing harness probes the same engine read as the `gravity_compensation` capability ([testing.md](testing.md)).
  - `get_motors_state()` — read the current state (same three values) so a caller can check **before** calling a movement verb, rather than discovering it via the fail-fast error. Returns the daemon's `motor_control_mode` in JSON-friendly form; "ready to move" is `state == "enabled"`. The daemon status reflects a `set_motors_state` a fraction of a second later (about 0.2 s on hardware), so a read made immediately after a set can still return the previous state; a caller confirming a switch polls briefly.
  - **Hardware honors the state; the sim does not.** On a Reachy Mini Lite over USB (`reachy_mini` 1.10, default kinematics engine) `"disabled"` and `"enabled"` each read back as set, and the head goes limp or holds accordingly. The MuJoCo sim daemon ignores every motor-state change and keeps reporting `"enabled"` (headless and viewer alike). The live tier therefore asserts read + dispatch (a valid mode) on every target, and the exact dispatch→state mapping is pinned on the `fake` (`tests-e2e/test_api.py::test_motor_state_reads_and_dispatches_over_the_live_path`, which lowers the head to the SDK's sleep pose before torque goes off on hardware).

**Motor torque is an explicit precondition, enforced by fail-fast — not auto-managed.** The audio verbs (`say`, `audio_input`, `play_sound`) and the wobbling mode (`set_wobbling`) need no motors. `play_emotion` and `start_head_tracking` **move the robot**, so they require torque `Enabled`; if it isn't, they **raise `MotorsNotEnabledError`** rather than silently enabling motors or sending a command that does nothing. This is observable, not guessed: the daemon reports `motor_control_mode` ∈ `Enabled` / `Disabled` / `GravityCompensation` via the daemon client (`robot.client.get_status().backend_status` — the public `ReachyMini` has no motor-mode getter, so the Api reads it the way the SDK itself does), so a verb reads the *actual* state before acting. Reading rather than assuming is essential because the motor state is owned by the **daemon's** wake/sleep lifecycle, not by connecting: with `wake_up_on_start` (the sim/local daemon default) the daemon's boot sequence **enables** the motors just before the wake-up emote — so a freshly-started daemon reads `Enabled` — and `goto_sleep` (on stop, or an idle timeout) **disables** them again; a wireless robot instead boots asleep. Connecting (`__enter__`) itself changes nothing, so the bridge adds no auto-enable and needs no `is_awake` notion of its own — torque is a separate, observable, caller-owned concern (upstream details in [../docs/reachy-mini-api.md](../docs/reachy-mini-api.md)).

**Emotions library — delegated to the SDK, not re-implemented.** `play_emotion` / `list_emotions` wrap the upstream `reachy_mini.motion.recorded_move.RecordedMoves`, defaulting to its `DEFAULT_EMOTIONS_DATASET` (`pollen-robotics/reachy-mini-emotions-library`). Loading and caching are the SDK's: `RecordedMoves` resolves from the standard Hugging Face hub cache **offline-first** (`snapshot_download(..., local_files_only=True)`), falling back to a network download only on a cache miss — so the bridge keeps **no cache of its own**. Two things the implementation must honor: (1) constructing `RecordedMoves` does blocking disk/network IO, so the bridge builds it **lazily, once per connection** (cached instance, never at import) and off the event loop via `asyncio.to_thread` — and cancel-safe: a `list_emotions` / `play_emotion` cancelled during that first load does not discard it (the load is shielded, finishes in its thread, and the next call awaits the same in-flight load rather than starting a second download); (2) on a real/sim robot the daemon **preloads** the default datasets at startup, so the first call is normally a cache hit — on the `fake`/offline path the emotions library is stubbed (no HF access), consistent with [audio.md](audio.md)'s fake media. v1 keeps `play_emotion(name)` **literal** (name in → move played); the conversation app's compact-intent→move resolution and curated random-fallback pool are a caller/agent concern, not part of the bridge.

### Deferred to post-v1

Named here so the boundary is explicit; each is a straightforward addition once v1 lands:

- **Manual movement & gaze:** `look_at(...)` (image-pixel `look_at_image` / 3D-world `look_at_world` dispatch), `set_head_pose(roll, pitch, yaw, duration, ...)`, and composed gestures `nod(...)` / `shake_head(...)` / `turn(yaw, ...)`. These are what makes open question 1 (frame/units conventions) load-bearing — so that question is a **post-v1** concern. When they land they are primaries of the motion loop ([motion.md](motion.md)), not calls to upstream's `goto_target` (a daemon-side move, during which the daemon drops the loop's targets).
- **`wake()` / `sleep()`** — the upstream `wake_up()` / `goto_sleep()` personality emotes. Optional session bookends; not a prerequisite for anything (see torque note above). Both are daemon-side moves, so they pause the motion loop for their duration when they land.
- **`set_antennas(left, right, ...)`** — direct antenna control in degrees.
- **Rich perception:** `get_head_pose()`, `get_imu()`, `get_tracked_face()`, and sound direction of arrival (`get_sound_direction()` / DoA). Their return shapes settle with this batch, alongside [tools.md](tools.md) (see open questions). The camera frame (`get_camera_frame()`) is **no longer deferred** — it's in v1 scope above; v1 ships an agent that can hear, speak, follow a face, and read a camera frame, but still can't gaze from a pixel (`look_at_image`, above) or read pose/IMU/DoA.
- **`stop_talking()` — barge-in from outside the `say` task.** Cancelling the `say` task is the v1 stop, and a real one: `say` flushes the queued speaker audio (`media.audio.clear_player()`) and resets the wobbler before re-raising, so speech ends within the sink's buffer ([audio.md](audio.md)). What stays deferred is a verb that stops speech for a caller who does *not* hold the task (a tool call from an agent runtime, [tools.md](tools.md)): it needs the api to track its in-flight `say` task so `stop_talking()` can cancel it — a flush alone would let the still-running `say` push the rest of the utterance.

### Orchestration is the point

Verbs that don't map 1:1 to an upstream call are where this layer earns its keep. In v1 that's `play_emotion` resolving a name to a recorded move, checking torque first so the move actually plays (failing fast otherwise), playing it through the motion loop, and pausing tracking and wobbling around it; and the presence / breathing switches over that loop. The richer orchestration — `look_at` choosing the right upstream helper, `nod`/`shake_head` sequencing poses — arrives with the deferred movement verbs. Pure pass-throughs (e.g. `play_sound`, `set_wobbling`, and later `get_imu`) are thin by design.

## Open questions

1. **Frame/units conventions (post-v1).** Exact axes, origin, and angle conventions for the deferred manual gaze/pose verbs (`look_at` / `set_head_pose`), so tools and callers agree (upstream world frame: x forward, y left, z up). Settles when those verbs land.
2. **Perception return shapes (post-v1).** Return types for the *remaining* deferred perception verbs (`get_head_pose` / `get_imu` / `get_tracked_face` / DoA), settled alongside [tools.md](tools.md).
3. **A stop for `play_sound`.** `play_sound` returns once the file has started, so the sound outlives the call with no way to stop it — the one verb outside the "Cancellation" contract's two classes. Either it becomes a spanning verb (completes when the sound has been heard, cancel stops it — needs the file's end, from the local `playbin`'s duration/EOS or by decoding the file) or it gains a `stop_sound()` counterpart on [audio.md](audio.md)'s `MediaSession.stop_sound()`. Deferred until a caller needs it; the primitive exists either way.
