# Serialise the detection loop's transitions, own the accepted motor commands

**Status:** Done

Implements the worker-ownership and motor-transition contracts in [user_perception.md](../specs/vision/user_perception.md) ("The detection loop", "Lifecycle") and [bridge.md](../specs/core/bridge.md) ("Cancellation" — instant verbs, "Motors") and [motion.md](../specs/motion/motion.md) ("Motors"). Fixes R1 and R2 of the [repository consistency review of 2026-10-06](../analysis/20261006_repository-consistency-review.md): overlapping detection starts no longer leak a detector and a loop, and a cancelled `set_motors_state` no longer leaves the motion loop out of step with the torque it set. No public API changes; the other R items are separate plans.

## Scope

- `src/reachy_mini_bridge/face_detection.py` — `FaceDetection.start()` / `stop()` serialised through one `asyncio.Lock`; a start in flight counts as running for a second start, and a stop arriving during a start waits for it and then stops what it built.
- `src/reachy_mini_bridge/bridge.py` — `_sync_detection` serialised through the same discipline (one lock around the wanted-flags read and the start/stop), so two mode verbs scheduled together cannot both decide to start; `set_motors_state` submits an owned command (`_MotorCommands`, the `_WobblingSession` pattern: a FIFO tail of tasks, each the SDK call *and* the loop transition, drained at teardown) and awaits it shielded.
- `specs/vision/user_perception.md` — "The detection loop" / "Lifecycle": the transitions are serialised; a start in flight is a running loop to the next caller. Status `Implemented` → `Updated` while this plan is open.
- `specs/core/bridge.md` — "Cancellation" (instant verbs) and "Motors": an accepted motor command completes as a whole — the SDK call and the loop's pause/resume — past the caller's cancel, in order with later commands, and is drained before the motion session stops. Status `Implemented` → `Updated` while this plan is open.
- `tests/test_face_detection.py` — overlapping starts build one detector and run one loop; a stop during a start stops what the start built.
- `tests/test_bridge.py` — overlapping `set_face_detection(True)` / `start_head_tracking()` on `fake` leave one worker and one owned detector, and `stop()` leaves none; a `set_motors_state("enabled")` cancelled inside the SDK call still resumes the loop (targets flow after the cancel), the mirror for `"disabled"` still pauses it; a command cancelled then followed by its counterpart applies in order; teardown drains a pending command.
- This plan and [the plans index](_index.md).

## Steps

1. **Mark this plan `In progress`** here and in the index. Set `user_perception.md` and `bridge.md` to `Updated` with the spec edits of steps 2 and 4, in the same change as the code.

2. **Serialise `FaceDetection`'s transitions.** Add `self._transition = asyncio.Lock()` to `FaceDetection`. `start()` takes it for its whole body: the `running` check, the factory acquisition and the task creation. `stop()` takes it too: the cancel-and-await of the task, the acquisition cleanups and the releases. A start cancelled while waiting for the lock starts nothing (the existing `_acquire` cleanup covers a cancel inside the build). Keep `restart()` synchronous — it only swaps the factory the running loop reads at its next poll. Spec: in "The detection loop" state that `start()` / `stop()` are serialised — a second `start()` during one in flight waits and finds the loop running; a `stop()` during a start waits for the build and then stops the loop it started, so the session never holds two loops or an unreleased detector.

3. **Serialise the bridge's sync.** Give `ReachyMiniBridge` an `asyncio.Lock` (`_detection_sync`) that `_sync_detection` holds while it reads the wanted flags and starts or stops the loop. The mode verbs keep setting their flag before calling `_sync_detection` and restoring it on failure as today; with the lock, the second of two overlapping calls sees the loop the first started. The teardown path (`stack` callback → `detection.stop()`) goes through the loop's own lock, which is enough: a start that was in flight finishes under it and the stop that follows cleans up.

4. **Own the motor commands.** Add `_MotorCommands` next to `_WobblingSession`: `submit(state, apply)` chains a task on its tail (`await previous` with `return_exceptions=True`, then `await asyncio.to_thread(sdk_call)`, then the loop transition — `motion.resume()` for `"enabled"`, `motion.pause()` for the two resting states — the motion session captured at submit time, since `resume()` / `pause()` on a session that has since stopped only queue a command no thread reads). `set_motors_state` keeps its validation and the gravity-compensation check in the caller (they raise before anything is accepted), then `await asyncio.shield(commands.submit(...))`, so a cancel returns at once and the command completes as a whole. Failures surface to the caller when it is still waiting and are logged otherwise (the `_WobblingSession._observe` pattern). Register the session's drain (`await` the tail, exceptions swallowed) on the exit stack right after `motion.stop` is pushed, so it runs *before* the motion session stops. `_require_motion()` is read at submit time, not after the await. Spec: "Cancellation" instant verbs — the command "completes in its thread" becomes "completes as a whole: the SDK call and, for the motor verbs, the loop transition that belongs to it, in order with later commands"; "Motors" — the bridge drains accepted motor commands before it stops the motion session.

5. **Tests, each observed failing first.**
   - `test_face_detection.py`: a factory held on a `threading.Event`; two `start()` tasks released together build **one** detector and `running` reads true with one `face-detection` task among `asyncio.all_tasks()`; a `stop()` started while the factory is held completes after it and leaves the detector closed and no task.
   - `test_bridge.py`: on `fake` with a custom factory held the same way, `set_face_detection(True)` and `start_head_tracking()` gathered; after release, one detector was built; after `bridge.stop()` no `face-detection` task survives and that one detector received `close()`. The ordering case: `start_head_tracking()` gathered with `set_face_detection(False)` after a prior `True` leaves the loop running (tracking wants it).
   - Motors: the fake's `enable_motors` held on an event; cancel the `set_motors_state("enabled")` task while it is held; release; assert the motor state reads `enabled` **and** `robot.targets` grows afterwards (the loop resumed). The mirror: `"disabled"` cancelled inside the call still pauses (no new targets after the acknowledgement). Order: cancel an `"enabled"` inside its call, then call `"disabled"` at once; after release the state is `disabled` and the loop paused. Teardown: `stop()` with a command held completes after the release and the final command trace ends with that command.

6. **Flip the statuses** once the gate passes: this plan `Done`, `user_perception.md` and `bridge.md` back to `Implemented`, index rows in sync.
