# The bridge: `ReachyMiniBridge` and the `start()` / `stop()` lifecycle

**Status:** Done

Implements the settled design in [specs/core/bridge.md](../specs/core/bridge.md) ("Purpose", "Lifecycle") and its echoes in [specs/audio/audio.md](../specs/audio/audio.md) ("One media session, owned here"), [specs/motion/motion.md](../specs/motion/motion.md) ("Lifecycle"), [specs/vision/camera.md](../specs/vision/camera.md) ("The feed"), [specs/daemon/daemon.md](../specs/daemon/daemon.md) ("Public surface", "Teardown stops what the bridge started", "One implementation, two users"), [specs/testing/testing_support.md](../specs/testing/testing_support.md) ("Public surface") and [specs/examples/control_panel.md](../specs/examples/control_panel.md) ("Lifecycle"). It delivers two things in one change: the rename — `ReachyMiniApi` becomes `ReachyMiniBridge`, `api.py` becomes `bridge.py`, the `live_api` fixture becomes `live_bridge` — and the lifecycle pair — `start()` / `stop()` / `running` on the bridge with `async with` delegating to them, the same `async start()` / `async stop()` pair on every session the bridge owns, and `start_daemon` + `DaemonHandle.stop()` under `managed_daemon`. It deliberately leaves every verb, mode and behaviour as it is: nothing the robot does changes, only how the objects are named and brought up and down.

### The lifecycle pair

- `src/reachy_mini_bridge/bridge.py` — `async start()`, `async stop()`, the `running` property; `__aenter__` / `__aexit__` become the two-line wrappers; the bring-up becomes the uniform "start it, push its stop" list over the sessions' pairs.
- `src/reachy_mini_bridge/audio.py` — `MediaSession.start()` / `stop()` replace `__aenter__` / `__aexit__`.
- `src/reachy_mini_bridge/motion.py` — `MotionSession.start()` / `stop()` (async) replace `__aenter__` / `__aexit__` / the public `close()`.
- `src/reachy_mini_bridge/camera.py` — `CameraFeed.start()` / `stop()` become `async` (the join off the loop); `bind()` stays.
- `src/reachy_mini_bridge/daemon.py` — `start_daemon(...) -> DaemonHandle` and `DaemonHandle.stop()`; `managed_daemon` becomes the context-manager form over them.
- `src/reachy_mini_bridge/testing/fixtures.py` — `live_bridge` drives `start()` / `stop()`; `tests-e2e/test_custom_faces.py` likewise (it calls the dunders by hand today).
- `examples/control_panel/controller.py` — the loop task awaits `bridge.start()` and, in a `finally`, `bridge.stop()`.
- `tests/test_bridge.py`, `tests/test_audio.py`, `tests/test_motion.py`, `tests/test_head_tracking.py`, `tests/test_camera.py`, `tests/test_daemon.py`, `tests/test_testing_support.py`, `tests/test_control_panel.py` (or wherever the panel's tests live — `examples/control_panel/` tests) — the tests that drive the old shapes move to the new ones, plus the new functional tests listed under Verification.

## Steps

1. **The rename, mechanically, first** — one commit-sized step that changes no behaviour, so the lifecycle work that follows is reviewed on its own. `git mv` the module and the two test files; `git grep -n "ReachyMiniApi\|reachy_mini_bridge\.api\b\|specs/core/api\.md\|live_api\|test_api"` over `src tests tests-e2e examples docs README.md AGENTS.md` and rename every hit (the `/api/...` HTTP paths and `docs/reachy-mini-api.md`'s own name are not hits). Update the AGENTS.md project map row and the spec frontmatters. Run the full verification — everything must be green before step 2, with no test changed except for names.

2. **The daemon pair** (`daemon.py`). Split `managed_daemon` in two: `start_daemon(config, *, host, port, backend) -> DaemonHandle` does what the context manager's body does up to its `yield` — the `spawn` check, the port probe, the borrow-or-spawn decision, the readiness wait (stopping a child that fails it, as today) — and returns the handle; `DaemonHandle` gains a `stop()` method that runs today's `finally` (`_stop(proc)` then `output.stop()`) for an owned handle and nothing for a borrowed one, idempotent (a second call is a no-op). The handle stays a frozen dataclass with the same four public fields, so `DaemonHandle("127.0.0.1", 8000, owned=True, pid=4242)` equality in `tests/test_daemon.py` keeps holding: carry the process and the output reader as private fields excluded from `repr` and `eq` (`field(default=None, repr=False, compare=False)`). `managed_daemon` becomes `handle = start_daemon(...); try: yield handle; finally: handle.stop()`. `testing/_daemon.py` keeps using `managed_daemon` unchanged.

3. **The sessions' pairs.** In `audio.py`, rename `MediaSession.__aenter__` → `async start()` (returning `None`; "already open" stays `BridgeError`) and `__aexit__` → `async stop()` (a no-op when closed, as today's guard already makes it); delete the dunders; update the `_require_open` message. In `motion.py`, `async start()` starts the thread and `async stop()` runs today's `close()` under `asyncio.to_thread` (`close()` becomes the private `_close()`); delete the dunders; a `start()` on a started session raises `BridgeError`, a `stop()` on a never-started or stopped one is a no-op (a thread cannot be started twice — guard it). In `camera.py`, `start()` keeps its body and `stop()` runs the join under `asyncio.to_thread`; both become `async def`. `FaceDetection` already has the pair — leave it. `HeadTracker` has no pair by design (spec "Lifecycle") — leave it.

4. **The bridge's pair** (`bridge.py`). Move the body of `__aenter__` into `async def start(self) -> None` and the body of `__aexit__` into `async def stop(self) -> None`; `__aenter__` becomes `await self.start(); return self` and `__aexit__(self, *exc)` becomes `await self.stop()`. Add `running` (`self._exit_stack is not None`). Rewrite the bring-up as the uniform list, one step per session: `await x.start()` then `stack.push_async_callback(x.stop)` — the daemon through `handle = await cancel_safe_step(lambda: _daemon.start_daemon(...), lambda h: h.stop())` and `stack.push_async_callback(asyncio.to_thread, handle.stop)`; the robot as today (its build-and-enter is one step, upstream's object connecting in its constructor); the media session; the camera feed; wobbling; the detection loop; the motion session. The order, the `cancel_safe_step` wrapping of the blocking starts, the `except BaseException` unwinding and the mode reset in `stop()` are unchanged. `stop()` on a bridge that is not running returns at once (today's `if stack is not None` — keep the mode reset out of that path, so a `stop()` never touches a bridge that never started).

5. **The callers.** `testing/fixtures.py`: `asyncio.run(bridge.start())` / `asyncio.run(bridge.stop())`, no dunder calls; the same in `tests-e2e/test_custom_faces.py`. `examples/control_panel/controller.py` `_main`: `await self._bridge.start()` before the emotions cache and `await self._bridge.stop()` in the `finally` that today the `async with` provides — the `ready` future, the meters and the stop event keep their places. Every test that called `api.__aenter__()` by hand (`tests/test_bridge.py`, several) calls `bridge.start()`; those that cancel a bring-up (`asyncio.create_task(api.__aenter__())`) cancel `bridge.start()`.

6. **Tests.** Adapt the existing ones to the new shapes (the `async with MediaSession(robot)` / `async with MotionSession(...)` blocks in `tests/test_audio.py`, `tests/test_motion.py`, `tests/test_head_tracking.py` become `await session.start()` / `try: ... finally: await session.stop()`, or a small local `asynccontextmanager` helper in the test module; `tests/test_camera.py`'s `feed.start()` / `feed.stop()` become awaited). Add, on the `fake`:
   - `tests/test_bridge.py`: `start()` then `stop()` leaves the same recorded robot commands and the same end state as `async with` (the robot's motion loop ran, wobbling was disabled at the end, the modes are back at the config's); `running` is `False` before `start()`, `True` after, `False` after `stop()`, and `False` after a failed `start()`; `start()` twice raises `BridgeError` and the session is still usable; `stop()` on a never-started bridge is a no-op (no robot command recorded, no error); `stop()` then `start()` again works — a second session on the same object, `faces` and `camera` the same objects; cancelling `start()` mid-flight still unwinds everything (the existing cancellation test, moved onto `start()`).
   - `tests/test_daemon.py`: `start_daemon` on a scripted ready child returns an owned handle whose `stop()` terminates the process; `stop()` twice terminates once; a borrowed handle's `stop()` leaves the process alone; `managed_daemon` still passes every existing test unchanged.
   - `tests/test_motion.py` / `tests/test_audio.py` / `tests/test_camera.py`: `start()` twice raises (motion, media) or is a no-op (camera, as spec'd); `stop()` before `start()` is a no-op; after `stop()`, `latest()` is `None` (camera), `say` raises `BridgeError` (media), `submit` fails (motion).
   - The control panel's tests: `start()` / `stop()` on the controller still bring the bridge up and down (the existing tests cover this; one asserts the bridge is not running after `controller.stop()`).

7. **Docs.** README: the class name everywhere, `as bridge`, the repo table's `bridge.py`, and one sentence in the "Clean shutdown" row naming `stop()` as what leaving `async with` calls, with a two-line `start()` / `stop()` example for a host with its own lifecycle. `docs/testing-with-the-bridge.md`: `live_bridge`. `docs/custom-face-detector.md`, `docs/running-the-sim-daemon.md`: the class name.

8. **Statuses.** Once verification passes: flip `specs/core/bridge.md`, `specs/audio/audio.md`, `specs/vision/camera.md`, `specs/daemon/daemon.md`, `specs/testing/testing_support.md` and `specs/examples/control_panel.md` from `Updated` to `Implemented` (file and [specs/_index.md](../specs/_index.md) row); `specs/motion/motion.md` stays `Stable` (its own plan is still `In progress` on the on-robot checklist). Set this plan `Done` here and in [_index.md](_index.md); update the overview's roadmap item.
